### 영속성 컨텍스트

- _**엔티티를 영구 저장하는 환경**__ _이라는 뜻) 논리적인 개념!

- EntityManager.persist(entity) → 단순히 데이터베이스에 엔티티를 저장한다는 뜻 x → **영속성 컨텍스트를 통해 엔티티를 영속화한다 ****   ** = 엔티티를 디비에 저장하는 것이 아닌 영속성 컨텍스트에 저장한다.

> J2SE(Java 2 Platform, Standard Edition)는 자바 프로그래밍 언어의 표준화 된 플랫폼 및 런타임 환경

### 엔티티의 생명주기

- 비영속 (new/transient) - 영속성 컨텍스트와 전혀 관계가 없는 **새로운 상태** EntityManager.persist(entity) 하게 되면 영속화 되는 것.

- 영속(managed) - 영속성 컨텍스트에 **관리**되는 상태

- 준영속(detached) - 영속성 컨텍스트에 저장되었다가 **분리**된 상태

- 삭제(removed) - 삭제된 상태

![image](/assets/images/d6b4133c377a409d9b3cdf751d5d370e.png)

---

#### 1. 비영속

: JPA 와 관련이 없는, 객체 생성만 한 상태

{% raw %}
```java
//객체를 생성한 상태(비영속) 
Member member = new Member(); 
member.setId("member1"); 
member.setUsername("회원1");
```
{% endraw %}

#### 2. 영속

: 영속성 컨텍스트에 추가.   
* 영속화한다고 데이터베이스에 바로 저장되는 것은 아님!  
→ 실제 커밋이 이루어져야 저장

{% raw %}
```java
// 위에서 이어
EntityManager em = emf.createEntityManager();
em.getTransaction().begin();
//객체를 저장한 상태(영속)
em.persist(member);
```
{% endraw %}

#### 3. 준영속, 삭제

{% raw %}
```java
// 회원 엔티티를 영속성 컨텍스트에서 분리, 준영속 상태 
em.detach(member);
 
// 객체를 삭제한 상태(삭제)
// 실제 데이터베이스에서도 삭제 요청
em.remove(member);
```
{% endraw %}

### 엔티티 조회, 1차 캐시

- 영속성 컨텍스트의 데이터 조회는 1차 캐시에서부터 이루어진다.

- 조회 단계
    1. 비영속 상태의 엔티티를 생성한 후 **영속화 **→ 1차 캐시에 저장

    1. 데이터 조회 시 **1차 캐시를 우선 조회**, 캐시 내에 존재한다면 캐시 값 반환

    1. 1차 캐시에 원하는 데이터가 없다면 데이터베이스에서 조회
          1. 1차 캐시 조회

          1. 데이터 없을 경우 DB 조회

          1. 1차 캐시에 조회된 데이터 저장

          1. 데이터 반환

![image](/assets/images/6bd4935780314e6585e99557790438fa.png)

{% raw %}
```java
// 엔티티를 생성한 상태(비영속) 
Member member = new Member(); 
member.setId("member1"); 
member.setUsername("회원1");

// 엔티티를 영속 (1차 캐시에 저장)
em.persist(member);

// 1차 캐시에서 조회
Member findMember = em.find(Member.class, "member1");
// 데이터베이스에서 조회
Member findMember2 = em.find(Member.class, "member2");
```
{% endraw %}

> 💡 EntityManager 는 하나의 트랜젝션이 곧 생명주기이다.
> 요청 하나가 들어오는 경우 하나의 영속 컨텍스트(곧 EntityManager) 가 생성되어 관리되고, 해당 요청이 종료되게 되면 영속 컨텍스트 또한 삭제된다.

#### 영속 엔티티의 동일성 보장

> 💡 영속 컨텍스트에서 조회한 동일 엔티티에 대해서 `==` 비교가 true 임을 보장함.

> _1차 캐시로 반복 가능한 읽기(REPEATABLE READ) 등급의 트랜잭션 격리 수준을 데이터베이스가 아닌 애플리케이션 차원에서 제공_

{% raw %}
```java
Member a = em.find(Member.class, "member1"); 
Member b = em.find(Member.class, "member1");
System.out.println(a == b); //동일성 비교 true
```
{% endraw %}

### 엔티티 등록 - 트랜젝션을 지원하는 쓰기 지연

- 엔티티매니저는 데이터 변경 시 트랜잭션을 시작해야 한다.

- 새로운 엔티티를 엔티티매니저에 등록하여도, 트랜젝션을 통해 커밋하기 전까지는 Insert SQL 을 보내지 않는다.
    - 쓰기 지연 SQL 저장소에 SQL 저장

    - transaction.commit(); 실행 시 :  SQL 저장소에 저장되어 있던 SQL 들이 flush 되고, 데이터베이스에 commit 되어 SQL 실행

- 이유) 버퍼링 기능을 사용할 수 있다(최적화 가능)
    - persistence.xml 파일 내 옵션으로 버퍼링 가능

    - <property name=”hibernate.jdbc.batch_size” value=”10”>
          - 10개씩 모아서 데이터베이스에 커밋

{% raw %}
```java
EntityManager em = emf.createEntityManager();
EntityTransaction transaction = em.getTransaction();

//엔티티 매니저는 데이터 변경시 트랜잭션을 시작해야 한다.
transaction.begin(); // [트랜잭션] 시작

em.persist(memberA);
em.persist(memberB);
//여기까지 INSERT SQL을 데이터베이스에 보내지 않는다.

//커밋하는 순간 데이터베이스에 INSERT SQL을 보낸다.
transaction.commit(); // [트랜잭션] 커밋
```
{% endraw %}

### 엔티티 수정 - 변경 감지(**Dirty Checking)**

- JPA - 자바 컬렉션처럼 사용 가능한 것도 목적이 있다
  → 컬렉션에 있는 객체(ex.list) 값을 변경할 때 update 하려고 별도의 put 을 하거나 하지 않는다.

- JPA 도 동일. set 해준 뒤 별도의 update | persist 등의 동작을 하지 않고,  자동으로 변경을 감지하여 update 실행
    - transaction.commit 시 flush() 실행 → 엔티티와의 스냅샷 비교 → 변경 있을 시 update 호출

    - **그냥 커밋 시점에 알아서 변경 감지하고 바꿔주는구나~ 라고 이해하면 된다!**

    - **Dirty Checking**

{% raw %}
```java
EntityManager em = emf.createEntityManager();
EntityTransaction transaction = em.getTransaction();
transaction.begin(); // [트랜잭션] 시작

// 영속 엔티티 조회
Member memberA = em.find(Member.class, "memberA");

// 영속 엔티티 데이터 수정
memberA.setUsername("hi");
memberA.setAge(10);

// em.update(member) 이런 코드가 있어야 하지 않을까?
// 또는 em.persist(memberA); 를 해야 할 것 같다.
transaction.commit(); // [트랜잭션] 커밋
```
{% endraw %}

### 플러시(flush)

- **영속성 컨텍스트의 변경내용을 데이터베이스에 반영(동기화)**

- 커밋 직전에 지금까지의 변경사항을 동기화해주는 것이라고 본다.

#### 플러시 발생 시 이루어지는 작업

- 변경 감지

- 수정된 엔티티 쓰기 지연 SQL 저장소에 등록

- 쓰기 지연  SQL 저장소의 쿼리를 데이터베이스에 전송 (등록/수정/삭제)

#### 영속성 컨텍스트를 flush 하는 방법

- **em.flush() - flush 직접 호출**
    - 이거 한다고 1차 캐시가 지워지거나 하지는 않는다!

- **트랜잭션 커밋 - flush 자동 호출**

- **JPQL 쿼리 실행 - flush 자동 호출**
    - transaction.commit() 하기 전에 우리는 데이터베이스에 컨텍스트 내용이 반영되지 않음을 알고 있다.

    - JPQL 은 쿼리를 SQL 로 번역해서 DB에 직접 조회한다. → 만약, 하나의 트랜잭션에서 em.persist() 이후 JPQL 을 실행한다면? → 반영되지 않은 컨텍스트의 내용으로 오류가 발생할 수 있다.

    - **이를 방지하기 위해서 JPQL 실행시 우선적으로 flush() 를 실행한다.**

{% raw %}
```java
em.persist(memberA);
em.persist(memberB);
em.persist(memberC);
//중간에 JPQL 실행
query = em.createQuery("select m from Member m", Member.class);
List<Member> members= query.getResultList();
```
{% endraw %}

* `EntityTransaction.commit()` 실행 시 따라가보면 이런 로직이 이루어진다.

![image](/assets/images/f6ffddd5b5d1448b8db5e464db05e826.png)

> 💡 궁금한것) JPQL 로 실행되어 얻어온 객체들은 1차 캐시에 저장되는가?
> (GPT 대답)
>
> **JPA에서 JPQL을 사용해 조회한 객체들 역시 영속성 컨텍스트(1차 캐시)에 저장됩니다. JPA의 기본 동작 원칙은 "영속성 컨텍스트에서 관리되는 엔티티를 반환"하는 것이기 때문입니다.**
>
> **따라서, 위의 코드에서 **`query.getResultList()`**를 통해 반환된 **`members`** 리스트에 포함된 **`Member`** 객체들은 모두 영속성 컨텍스트에 포함되어 있습니다.**
>
> **그러나 주의할 점은, 이는 조회 시점에 해당 엔티티가 영속성 컨텍스트에 없었을 경우입니다. 만약 JPQL로 조회하기 전 해당 엔티티가 이미 영속성 컨텍스트 내부에 있다면, 그 엔티티는 1차 캐시에서 가져와집니다.**
>
> **즉, 아래와 같은 순서로 동작합니다:**
>
> **JPQL 실행.****결과 리스트를 받아옴.****각각의 결과 항목들을 체크하여 이미 1차 캐시(영속성 컨텍스트) 내부에 있는지 확인.****만약 있으면, 그것을 사용하고 없으면 DB에서 가져옴.****DB에서 가져오면 그것을 1차 캐시에 저장하고 그것을 반환.**
>
> **따라서 위 코드 상황에서 **`memberA`**, **`memberB`**, **`memberC`** 등이 이미 persist 되어있으므로 이들 객체는 1차 캐시 내부에 있습니다. 이 후 실행된 JPQL 결과로 돌아오는 멤버들 중 이 세 객체가 포함되어 있다면, 그 객체 정보는 실제 DB 가 아닌 1차 캐시에서 가져오게 됩니다.  
>   
> —-  
>   
> JPQL 사용하면 1차 캐시 안 들리고 가나?(질문)  
> → 들린다는데?**

#### 플러시 모드 옵션

{% raw %}
```java
em.setFlushMode(FlushModeType.COMMIT) // 플러시 모드 설정
```
{% endraw %}

- 모드 종류
    - **FlushModeType.AUTO** 커밋이나 쿼리를 실행할 때 플러시 (기본값)

    - **FlushModeType.COMMIT** 커밋할 때만 플러시

- ⚠️**그냥 기본값으로 두고 쓰자.**

### 준영속 상태

- 영속 상태의 엔티티가 영속성 컨텍스트에서 분리(detached)

- 영속성 컨텍스트가 제공하는 기능을 사용하지 못한다.

{% raw %}
```java
Member member = em.find(Member.class, 100L); // 영속
member.setName("NEW_NAME");

em.detach(member); // 비영속 전환

// 데이터베이스에 커밋 -> 비영속된 member은 update 되지 않는다.
tx.commit();
```
{% endraw %}

#### 준영속 상태로 만드는 방법

- em.detach(entity) 특정 엔티티만 준영속 상태로 전환

- em.clear() 영속성 컨텍스트를 완전히 초기화(1차 캐시를 비움)

- em.close() 영속성 컨텍스트를 종료
