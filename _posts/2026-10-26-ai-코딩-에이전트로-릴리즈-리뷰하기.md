## 릴리즈 전날, 한 명이 한 번에 다 보기엔 범위가 넓다

배포 직전 리뷰는 보통 범위가 크다. 커밋 수십 개, 설계 문서, 작업 항목, 릴리즈노트, 인프라 설정 변경이 한꺼번에 섞여 있다. 한 사람이 처음부터 끝까지 읽으면 두 가지가 생긴다.

- 앞부분에서 본 내용이 뒤에서는 흐려지고, 읽은 순서가 판단에 영향을 준다.
- 의존성 변경, 메시지 큐, 문서 일치 같은 서로 다른 관점이 한 사람의 머릿속에서 섞인다.

최근 한 번의 릴리즈에서 AI 코딩 에이전트 여러 개를 **역할별로 나누고 서로의 결과를 교차 검증**하는 방식으로 리뷰를 해 보았다. 회사 업무 내용은 빼고, 이 방식에서 효과가 있었던 운영 요령만 정리한다.

> 에이전트 제품과 모델은 계속 바뀐다. 아래 내용은 특정 도구에 의존하지 않는 방법론 위주로 적었다.

---

## 1. 한 에이전트에 한 역할만 준다

처음에는 "릴리즈 전체를 리뷰해 줘"라고 시키고 싶은 유혹이 있다. 하지만 이렇게 쓰면 요약이 얕아진다. 대신 역할을 쪼갰다.

| 역할 | 맡긴 일 | 돌려받는 것 |
|---|---|---|
| Git 조사 | 기준 브랜치 대비 커밋과 diff 목록 정리 | 커밋 표, 버전·설정·의존성 변경 목록 |
| 문서 조사 | 이번 범위에서 추가·수정된 설계/구현 문서 정리 | 문서별 목적, 상태, 미검증 항목 |
| 작업 항목 조사 | 문서와 커밋이 가리키는 작업 항목 확인 | 실제로 작업한 항목만의 목록 |
| 회귀 검사 | 과거에 문제가 많았던 영역과 이번 변경 대조 | 과거 패턴 대비 판정 표 |
| 코드 리뷰 | 신규 코드에 대한 독립 리뷰 | 심각도 태그가 붙은 지적 목록 |
| 의존성 검사 | 라이브러리 상향의 호환성 확인 | 버전 표, 영향 있는 동작 변경 |

역할을 나누면 프롬프트가 짧고 선명해진다. "무엇을 모르는 채 시작하는가"가 서로 다르므로, 한 에이전트의 실수가 다른 에이전트의 결론에 번지는 일도 줄어든다.

---

## 2. 모든 에이전트를 READ-ONLY로 시작한다

가장 먼저 넣은 규칙은 쓰기 금지다. 리뷰 에이전트가 파일을 수정하거나 브랜치를 바꾸기 시작하면 리뷰 대상 자체가 흔들린다. 프롬프트 첫 줄에 역할과 금지 사항을 함께 둔다.

{% raw %}
```text
역할: 신규 메시지 큐 코드 독립 리뷰 (READ-ONLY).
파일 수정, commit, checkout 금지.
저장소: <경로>
대상: 커밋 <hash> 와 관련 설계/구현 문서.
쉘: PowerShell 5.1 이므로 && 와 || 를 쓰지 말고 ; 로 연결한다.
출력: 파일:줄 단위 지적, 심각도(High/Med/Low), 근거 코드, 권장 조치.
```
{% endraw %}

규칙은 프롬프트 말만으로 끝내지 않는 편이 좋다. 도구 쪽에서도 확인한다.

- 에이전트에게 쓰기 권한이 필요 없다면 도구 권한 자체를 읽기 전용으로 준다.
- 환경에 따라 쉘 문법이 다르다. 프롬프트에 쉘 종류와 금지 문법을 적어 두면 실행 실패로 시간을 낭비하지 않는다.
- 외부 시스템(브로커, 클러스터)을 확인시킬 때도 조회 명령만 허용한다. 이번에는 큐 상태를 읽기 전용으로 조회해서 문서로만 보던 내용을 실제 상태와 대조할 수 있었다.

리뷰 결과에서 수정이 필요하다고 판단하면 **리뷰 에이전트가 아니라 메인 세션에서** 수정한다. 읽는 쪽과 쓰는 쪽을 분리하는 것이 목적이다.

---

## 3. 서로 다른 에이전트의 결과를 교차 검증한다

이번 방식에서 가장 가치가 컸던 부분이다. 서로 다른 도구(제품)의 에이전트에게 같은 코드를 읽게 하자 결론이 달랐다.

### 사례: 같은 지적, 다른 심각도

한 에이전트가 이렇게 지적했다.

> [P2] 호출자는 6초에 404를 받는데, 수신 쪽은 큐 대기 시간을 빼지 않고 새 5초 timeout을 준다. 실제 종료는 약 9.8초에 일어날 수 있다.

다른 에이전트에게 같은 지적을 보여 주고 반문하게 했더니 이런 답이 왔다.

> 지적은 코드상 맞다. 다만 배포를 막을 정도는 아니다. P3로 보고 후속 수정을 권장한다.

코드 지적 자체는 두 쪽 모두 맞다고 봤다. 갈린 것은 **영향도 판단**이었다. 이럴 때는 어느 쪽 말을 믿을지가 아니라, 판단의 근거를 나눠서 본다.

| 확인 항목 | 누가 맞는지 |
|---|---|
| 코드가 실제로 그렇게 동작하는가 | 코드를 직접 읽어 확인한다 |
| 그 경로가 실제 운영에서 발생하는가 | 로그와 실환경 상태로 확인한다 |
| 발생했을 때 피해가 어느 정도인가 | 사람이 판단한다 |

결과적으로 "코드 지적은 사실, 우선순위는 후속 항목"으로 정리했다. 에이전트 한 개만 썼다면 P2로 배포가 지연되거나, 반대로 놓칠 수 있었다.

### 교차 검증의 규칙

- 에이전트의 요약을 믿지 않는다. **중요한 주장은 메인 세션이 원본 코드에서 직접 확인한다.** 이번에도 리뷰 결과 중 핵심 두 가지(큐 선언 속성, 만료 판정 창)는 직접 코드를 열어 확인했다.
- 에이전트가 쓴 "확실성" 표기를 활용한다. 재현을 실행하지 않고 소스만 읽은 지적은 그렇게 표시하게 한다. "코드로 확인한 경쟁이다, 재현 테스트는 실행하지 않았다" 같은 문장이 있으면 신뢰 수준을 바로 알 수 있다.
- 테스트가 통과한 사실과 시나리오를 검증한 사실을 구분한다. 한 지적에서는 기존 테스트가 개별 경로만 따로 검증하고 있어, 순서를 강제하는 경쟁 시나리오 테스트가 없다는 점이 지적되었다.

## 4. 이전 장애 목록을 체크리스트로 쓴다

회귀 검사 에이전트에게 가장 효과적이었던 입력은 "과거에 우리가 겪은 문제 목록"이었다. 일반적인 "버그 없나 봐 줘"보다 훨씬 구체적인 결과가 나온다.

프롬프트에 넣은 정보는 이런 형태다.

{% raw %}
```text
이 서비스는 과거 메시지 큐 문제가 많았다.
- 세션이 끝난 뒤에도 큐가 남는 문제 → auto-delete 선언
- 같은 세션의 중복 구독으로 큐 폭증 → 중복 SUBSCRIBE 차단
- 정리 스케줄러가 사용 중인 큐를 삭제 → if-unused 조건
위 패턴 각각에 대해, 이번 변경이 같은 문제를 다시 만들 수 있는지 코드와 설정으로 판정하라.
```
{% endraw %}

결과는 표로 받는다. 각 행이 "과거 패턴 / 원인 / 이번 변경에서의 판정 / 근거 파일:줄"이면 사람이 한눈에 검토할 수 있다. 판정이 "안전함"이라면 근거가 반드시 따라와야 한다. 근거 없는 "안전하다"는 가장 위험한 문장이다.

팀의 장애 기록이나 지식 노트를 이 입력으로 연결해 두면, 리뷰 품질이 올라가는 동시에 기록의 가치도 같이 올라간다.

## 5. 긴 출력은 파일로 남기고, 파일에서 읽는다

릴리즈 리뷰에는 로그와 테스트 출력이 길다. 이것을 에이전트 컨텍스트에 그대로 넣으면 두 가지가 나빠진다.

- 컨텍스트가 소모되어 뒤쪽 지시를 놓치기 쉬워진다.
- 요약이 요약을 낳으면서 원본 근거가 사라진다.

그래서 다음 규칙을 썼다.

1. 테스트나 로그 명령의 **원본 출력은 작업용 폴더의 파일로 저장**한다.
2. 명령의 종료 코드를 보존한다. 필터링하거나 파이프로 넘기면 종료 코드가 사라질 수 있으니 따로 기록한다.
3. 에이전트에게는 파일 경로와 읽을 범위(시간 구간, 패턴, 줄 범위)를 준다.
4. 돌려받는 보고서에는 명령, 종료 코드, 실행 시각, 실패 목록, 원본 파일의 줄 번호를 포함시킨다.
5. 같은 명령을 위임하려고 다시 실행하지 않는다. 이미 있는 로그를 분석하고, 코드가 바뀌었을 때만 다시 돌린다.

{% raw %}
```text
저장: test-run-1.log (명령, 종료 코드, 실행 시각을 첫 줄에 기록)
읽기: 'FAILED' 패턴과 앞뒤 20줄, 그리고 마지막 100줄
반환: 실패 테스트 목록 + 각 실패의 스택 트레이스 첫 10줄 + 원본 파일 줄 번호
```
{% endraw %}

이렇게 하면 에이전트의 요약이 의심스러울 때 원본을 바로 열어 볼 수 있다. 요약은 길 찾기용 지도이고, 판단의 근거는 원본이어야 한다.

## 6. 가벼운 작업은 가벼운 모델에, 판단은 위에서

비용과 속도도 고려해야 한다. 로그가 수십만 줄인 분석을 가장 큰 모델에 통째로 맡기는 것은 낭비다.

| 작업 유형 | 적합한 방식 |
|---|---|
| 대량 로그 분류, 패턴 집계, 명령 실행과 결과 수집 | 가벼운 모델에게 맡기고 사실과 증거만 돌려받는다 |
| 코드 변경, 일반 코드 리뷰 | 중간 수준 모델 |
| 복잡한 진단, 동시성, 보안, 설계 판단 | 가장 강한 모델이나 메인 세션 |

가벼운 모델에게는 **판단 대신 사실**을 요구한다. "원인이 뭐냐"가 아니라 "이 패턴이 몇 번, 어느 시간대에, 어떤 상태 코드로 나왔는가"를 묻는다. 해석은 메인 세션이 한다. 가벼운 모델이 막히거나 애매한 결과를 내면 같은 일을 반복시키지 않고 위로 넘긴다.

---

## 7. 메인 세션의 역할

서브에이전트를 쓴다고 사람이나 메인 세션이 할 일이 없어지지는 않는다. 오히려 다음이 메인 세션의 몫이 된다.

- 역할과 범위를 정하고, 각 에이전트에게 필요한 맥락만 준다.
- 결과를 받으면 **원본 근거를 일부 직접 확인**한다.
- 서로 다른 결론을 비교해 우선순위를 정한다.
- 확인하지 못한 부분을 숨기지 않고 최종 보고서에 적는다.

에이전트에게 모르는 정보가 있으면 그것은 사람에게 되묻게 하는 편이 좋다. 이번에는 배포 대상 서버 수, 사용 중인 미들웨어, 테스트 결과 위치를 에이전트가 먼저 질문해서 리뷰 전제가 바로잡혔다. 코드만 보고 가정하는 것보다 훨씬 빠르다.

## 정리

| 원칙 | 구체적 방법 |
|---|---|
| 역할 분리 | 한 에이전트에 한 관점. Git, 문서, 작업 항목, 회귀, 코드, 의존성 |
| 읽기 전용 | 프롬프트와 도구 권한 양쪽에서 쓰기 금지. 수정은 메인 세션에서 |
| 교차 검증 | 서로 다른 도구의 결과를 비교하고, 핵심 주장은 원본에서 직접 확인 |
| 과거 장애 활용 | 이전 문제 목록을 체크리스트로 주고 표로 판정받는다 |
| 긴 출력 | 파일로 저장하고 범위를 지정해 읽는다. 종료 코드와 실행 시각을 남긴다 |
| 모델 배분 | 사실 수집은 가볍게, 판단은 위에서 |
| 책임 | 최종 결론과 보고는 메인 세션이 진다. 확인 못 한 것은 명시한다 |

AI 리뷰의 목적은 사람의 판단을 대체하는 것이 아니라, 사람이 **근거를 빠르게 모으고 서로 부딪히는 의견을 볼 수 있게** 하는 것이다. 에이전트의 확신 있는 문장이 근거 있는 문장은 아니라는 점만 기억하면, 역할 분리와 교차 검증은 릴리즈 전날의 부담을 꽤 줄여 준다.
