빌드 파이프라인에 Dependency-Track(이하 DT)을 붙여 두면 릴리스마다 SBOM이 올라가고, 알려진 취약점 목록이 나온다. 처음 그 목록을 열어 보면 숫자가 크다. 우리 프로젝트도 한 번에 68건이 나왔고, 취약 컴포넌트는 23개였다. 분석 상태(`analysis.state`)는 전부 비어 있었다.

이 글은 그 68건을 어떻게 줄였는지, 그리고 남은 항목을 **VEX**로 정리하는 방법을 다룬다. 마지막에는 실무에서 걸렸던 함정을 적었다.

## VDR과 VEX는 무엇이 다른가

CycloneDX에서는 둘 다 `vulnerabilities` 배열로 표현한다. 형식이 아니라 **담는 내용과 목적**이 다르다.

| 구분 | VDR (Vulnerability Disclosure Report) | VEX (Vulnerability Exploitability eXchange) |
|---|---|---|
| 질문 | 이 소프트웨어에 알려진 취약점이 **무엇이 있는가** | 그 취약점이 이 소프트웨어에서 **실제로 악용될 수 있는가** |
| 핵심 필드 | 취약점 ID, 심각도, 영향받는 컴포넌트(`affects`) | 위 필드 + `analysis`(상태, 근거, 대응) |
| 만드는 쪽 | 스캐너(DT 등)가 자동 생성 | 사람이 판단해서 작성 |
| 읽는 쪽 | 보안팀 | 보안팀, 고객, 감사 |

정리하면 VDR은 **스캐너의 출력**이고 VEX는 **그 출력에 대한 사람의 판정**이다. 스캐너는 "이 버전에 취약점이 있다"까지만 안다. 우리 코드가 그 취약한 기능을 호출하는지는 모른다.

## 전체 흐름

{% raw %}
```text
1. 파이프라인이 SBOM을 DT에 업로드
2. DT가 취약점 목록(VDR)을 만든다            -> 68건
3. 수정판이 있는 것은 의존성 버전을 올린다   -> 54건 해소
4. 남은 것은 코드에서 도달 가능한지 확인한다 -> 14건
5. 도달 불가 또는 오탐은 VEX로 판정한다      -> not_affected, false_positive
```
{% endraw %}

먼저 해야 할 일은 VEX가 아니라 **버전 상향**이다. VEX는 "고칠 수 없거나 고칠 필요가 없는" 항목에만 쓴다.

## 1단계: 고칠 수 있는 것은 올린다

판단 기준은 단순하게 잡았다.

- 수정 버전이 공개되어 있고, 같은 메이저/마이너 라인에서 올릴 수 있으면 **상향**한다.
- 수정 버전이 없거나 상향 비용이 크고, 코드상 도달 불가가 확인되면 **VEX**로 처리한다.

Spring Boot처럼 BOM이 버전을 관리하는 경우에는 버전 속성을 덮어쓰는 방식이 편하다.

{% raw %}
```xml
<properties>
    <!-- BOM 관리 버전을 취약점 수정판으로 덮어쓴다 -->
    <tomcat.version>10.1.x</tomcat.version>
    <netty.version>4.1.x.Final</netty.version>
</properties>
```
{% endraw %}

상향 후에는 다시 취약점 DB(OSV 등)에 조회해서 **남은 항목이 VEX 대상과 같은지** 확인한다. 이 확인이 없으면 "상향해서 줄었다"는 말을 근거 없이 하게 된다.

Boot 메이저 버전을 올리는 브랜치가 따로 있다면 주의하자. 한 BOM 기준으로 쓴 오버라이드가 다른 BOM에서는 맞지 않을 수 있다. 예를 들어 서블릿 컨테이너 메이저 버전을 덮어쓰는 속성이 그대로 합쳐지면, 기동 불가가 된다. 병합 후에는 `mvn dependency:tree`로 실제 해석된 버전을 확인한다.

## 2단계: 남은 항목을 판정한다

남은 14건은 항목마다 코드를 확인하고 판정했다. 근거는 "정적 코드 확인"이다.

| 유형 | 판정 | 예시 근거 |
|---|---|---|
| 취약 기능을 호출하지 않음 | `not_affected` / `code_not_reachable` | 특정 뷰 기술, 특정 라우팅 API를 사용하지 않음 |
| 입력이 통제됨 | `not_affected` / `protected_by_mitigating_control` 등 | 정렬 컬럼을 고정 값으로만 쓰고 사용자 입력이 닿지 않음 |
| 전이 의존성이며 해당 API 미호출 | `not_affected` / `code_not_reachable` | 클라이언트 라이브러리가 끌고 온 압축 라이브러리를 직접 호출하지 않음 |
| 권고가 철회됨 | `false_positive` | advisory가 철회되었는데 스캐너 DB에 남아 있음 |

여기서 중요한 것은 `not_affected`가 "우리는 괜찮다"는 선언이 아니라 **근거와 함께하는 판정**이라는 점이다. 근거 없는 `not_affected`는 나중에 가장 위험한 기록이 된다.

판정은 영구적이지 않다. 판정 근거가 된 코드 사용이 바뀌면 다시 판정해야 한다. 예를 들어 "해당 기능을 쓰지 않는다"는 근거였다면, 그 기능을 도입하는 PR에서 VEX를 재검토해야 한다.

## 3단계: VEX 파일 만들기

CycloneDX VEX의 핵심은 `analysis`다.

{% raw %}
```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "version": 1,
  "vulnerabilities": [
    {
      "id": "CVE-2026-00000",
      "source": { "name": "NVD", "url": "https://nvd.nist.gov/" },
      "analysis": {
        "state": "not_affected",
        "justification": "code_not_reachable",
        "detail": "해당 API를 호출하는 코드가 없음을 정적 검색으로 확인함"
      },
      "affects": [
        { "ref": "<VDR의 컴포넌트 bom-ref>" }
      ]
    }
  ]
}
```
{% endraw %}

`analysis.state`의 값은 다음과 같다. (CycloneDX 1.5 기준이고 스펙 버전에 따라 다를 수 있다.)

| state | 의미 |
|---|---|
| `exploitable` | 악용 가능하다. 조치가 필요하다. |
| `in_triage` | 분석 중이다. |
| `not_affected` | 영향받지 않는다. `justification`이 필요하다. |
| `false_positive` | 오탐이다. |
| `resolved` | 수정되었다. |

`justification`에는 `code_not_present`, `code_not_reachable`, `requires_configuration`, `requires_environment`, `protected_at_runtime` 등이 있다. 처리할 수 없지만 위험을 받아들이는 항목이라면 `response`(`will_not_fix` 등)를 쓴다.

### DT가 export한 VEX는 analysis가 비어 있다

가장 먼저 만난 함정이다. DT에서 프로젝트의 VEX를 export하면 취약점 목록은 들어 있지만, 아직 아무도 분석하지 않았으므로 **`analysis`가 비어 있다.** 이 파일을 그대로 import해도 아무 일도 일어나지 않는다.

그래서 흐름은 이렇게 된다.

1. DT에서 VEX(또는 VDR)를 export한다.
2. 판정 표를 기준으로 `analysis.state`, `justification`, `detail`을 **직접 채운다.**
3. 채운 파일을 DT에 올려 적용한다. (DT UI의 `Audit Vulnerabilities` 쪽 VEX 업로드/적용 기능. 메뉴 이름은 DT 버전에 따라 다를 수 있다.)

### 같은 취약점이 두 번 나올 수 있다

VDR을 확인하다가 같은 취약점 ID가 **같은 bom-ref로 두 번** 나오는 항목을 발견했다. VEX에서는 하나의 취약점 항목으로 합치고 `affects`에 두 컴포넌트를 나열했다.

{% raw %}
```json
{
  "id": "GHSA-xxxx-xxxx-xxxx",
  "analysis": { "state": "not_affected", "justification": "code_not_reachable" },
  "affects": [
    { "ref": "component-a-bom-ref" },
    { "ref": "component-b-bom-ref" }
  ]
}
```
{% endraw %}

파일을 만든 뒤에는 최소한 다음을 자동으로 확인했다. (스키마 validator는 돌리지 못했다는 점도 기록해 두었다.)

- VEX의 `affects.ref`가 VDR에 존재하는 bom-ref와 일치하는가
- 취약점 ID 개수와 `affects` 개수가 판정 표와 맞는가
- bom-ref가 중복되지 않는가

## 4단계: 새 버전에서는 다시 해야 할 수 있다

이 작업에서 가장 중요한 교훈이다.

**VEX 파일의 bom-ref는 DT가 프로젝트 버전마다 새로 부여하는 UUID라서 다른 버전에 재사용할 수 없다.** 그리고 새 프로젝트 버전을 업로드했을 때 이전 버전의 분석 상태가 자동으로 이어지지 않을 수 있다. (DT 버전과 설정에 따라 다를 수 있으므로 확인이 필요하다.)

그래서 우리는 **VEX 파일을 저장소에 보관하지 않기로** 했다. 대신 아래를 판정 근거 문서로 남긴다.

| 남기는 것 | 이유 |
|---|---|
| 취약점 ID, 컴포넌트, 버전 | 어느 항목인지 식별 |
| 판정(`not_affected` 등)과 `justification` | 결과 |
| 코드 확인 근거 | 재검증의 출발점 |
| 판정 날짜와 재판정 조건 | 유효 기간 |

새 버전의 VDR이 나오면, 그 VDR에서 같은 취약점을 찾아 이 표를 기준으로 VEX를 다시 만든다. 파일은 버전마다 재생성하고, **판단은 표에 남긴다.**

## 정리

| 단계 | 내용 |
|---|---|
| 1 | VDR로 현황 파악 (68건) |
| 2 | 수정판이 있으면 버전 상향 (54건 해소) |
| 3 | 상향 후 취약점 DB로 재조회해서 남은 항목 확인 |
| 4 | 남은 항목을 코드 확인 후 `not_affected` / `false_positive`로 판정 (14건) |
| 5 | export한 VEX의 빈 `analysis`를 채워 DT에 적용 |
| 6 | 판정 근거는 문서로, VEX 파일은 버전마다 재생성 |

체크리스트로 줄이면 이렇다.

- [ ] VEX보다 버전 상향이 먼저다.
- [ ] 상향 후 남은 취약점이 VEX 대상과 일치하는지 재조회했는가?
- [ ] `not_affected`에는 반드시 `justification`과 `detail`을 쓴다.
- [ ] export한 파일의 `analysis`가 비어 있지 않은지 확인했는가?
- [ ] VDR에서 중복된 항목을 병합했는가?
- [ ] 판정 근거를 파일이 아니라 문서에 남겼는가?
- [ ] 판정의 전제(사용하지 않는 기능)가 바뀌면 재판정하기로 했는가?

VEX는 취약점 숫자를 줄이는 도구가 아니다. "이 항목은 확인했고, 이런 이유로 영향이 없다"는 것을 **다음 사람이 검증할 수 있는 형태로 남기는** 도구다. 숫자를 맞추려고 쓰기 시작하면 오히려 가장 먼저 신뢰를 잃는다.
