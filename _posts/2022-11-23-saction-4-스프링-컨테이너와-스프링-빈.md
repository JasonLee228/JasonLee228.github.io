### # 스프링 컨테이너와 스프링 빈

- 스프링 컨테이너의 생성 과정

1. AppConfig 클래스를 파라미터로, (구성 설정 정보로 지정) 스프링 컨테이너 생성 

{% raw %}
```java
ApplicationContext applicationContext 
												= new AnnotationConfigApplicationContext(AppConfig.class);
```
{% endraw %}

![image](/assets/images/a3f53d863388446a873fa80b0c78d543.png)

1. 스프링 빈 등록

> 📌 구성 설정 정보로 지정한 클래스 내부에서 @Bean 이 붙은 메소드를 전부 호출, 
> 메소드 명을 key 로, 해당 메소드에서 생성된 객체를 value로 지정하여 컨테이너에 저장.
> 저장된 객체를 ‘스프링 빈’ 이라고 한다.

> ⚠️ 스프링 빈의 이름
>
> - 빈 이름은 메서드 이름을 사용한다.
>
> - 빈 이름을 직접 부여할 수도 있다.
>   {% raw %}
>   ```java
>   @Bean(name="memberService2”)
>   ```
>   {% endraw %}
>
> 빈 이름은 위에서 말했듯 고유의 key로 사용된다. 때문에 모든 빈은 다른 이름을 사용해야 하며, 겹치는 이름이 발생할 경우 다른 빈을 무시하고 생성되거나, 충돌이 발생할 수 있다.

![image](/assets/images/730268e36ea9472aae0db462fa0c1bdd.png)

1. 스프링 빈 의존관계 설정

> ⚠️ 빈 사이의 의존관계 주입(DI)은 설정 정보 클래스를 참고해서 이루어진다.

![image](/assets/images/c4d8a6cc922a472f837367b12f7b6bd5.png)

### BeanFactory, ApplicationContext

![image](/assets/images/8f1bf36b46c1484b883e5a43dbe342fb.png)

- BeanFactory

> 💡 - 스프링 컨테이너의 최상위 인터페이스.
> - **스프링 빈을 관리하고 조회하는 역할** 담당

> 💡 - BeanFactory 기능을 모두 상속받아 제공
> - BeanFactory의 기능 뿐 아니라, 애플리케이션 개발을 위한 많은 부가기능을 제공하는 인터페이스.

### BeanDefinition - 스프링 빈 설정 메타 정보

- 스프링이 여러 가지 빈 설정 형식을 지원할 수 있게 하는 것
    - BeanDefinition 은 하나의 추상화로써 스프링 컨테이너가 어떤 설정 정보를 가지고 빈 설정을 했는지 알 필요가 없게 한 것. 

    - → 역할과 구현을 개념적으로 나눈 것!
          - 추상화 → BeanDefinition, 구체화 → 자바 코드 또는 XML

    - 스프링 컨테이너는 자바 코드를 통한 BeanDefinition인지, XML을 통한 BeanDefinition 인지 관심이 없고, 알 필요도 없다. 단지 BeanDefinition만 존재하면 된다.

- BeanDefinition, 빈 설정 메타 정보는  @Bean, <Bean> 당 각각 하나씩 생성됨.
    - 스프링 컨테이너는 이 메타 정보를 기반으로 빈을 생성함.

- `AnnotationConfigApplicationContext` 는 `AnnotatedBeanDefinitionReader` 를 사용해서 자바 설정 파일, AppConfig.class 를 읽고 BeanDefinition을 생성한다.

![image](/assets/images/e55650d5742442e18dc05760955e4cc4.png)

- `GenericXmlApplicationContext` 는 `xmlBeanDefinitionReader` 를 사용해서 XML 파일, AppConfig.xml 를 읽고 BeanDefinition을 생성한다.

![image](/assets/images/6792914196064ecdb62ec38c7b549b23.png)

- BeanDefinition 조회해 보기

</details>

> 💡 BeanDefinition 정보
>
> - BeanClassName: 생성할 빈의 클래스 명(자바 설정 처럼 팩토리 역할의 빈을 사용하면 없음)
>
> - factoryBeanName: 팩토리 역할의 빈을 사용할 경우 이름, 예) appConfig
>
> - factoryMethodName: 빈을 생성할 팩토리 메서드 지정, 예) memberService
>
> - Scope: 싱글톤(기본값)
>
> - lazyInit: 스프링 컨테이너를 생성할 때 빈을 생성하는 것이 아니라, 실제 빈을 사용할 때까지 최대한 생성을 지연처리 하는지 여부
>
> - InitMethodName: 빈을 생성하고, 의존관계를 적용한 뒤에 호출되는 초기화 메서드 명
>
> - DestroyMethodName: 빈의 생명주기가 끝나서 제거하기 직전에 호출되는 메서드 명
>
> - Constructor arguments, Properties: 의존관계 주입에서 사용한다. (자바 설정 처럼 팩토리 역할의 빈을 사용하면 없음)

> 💡 자바 설정 파일 등을 통해서 빈을 등록하는 방법 = 팩토리 메서드를 통해서 우회하여 등록하는 방법!
> → AppConfig라는 클래스 내의 메소드를 통해서 빈을 등록하기 때문에 스프링에서는 이 방법을 팩토리 메소드를 통해 빈 등록하는 방법이라고 한다.

- 직접 등록하는 방법과 팩토리 메소드를 통해서 등록하는 방법에서의 BeanDefinition 차이?

{% raw %}
```java
XML을 통한 빈 등록 시 BeanDefinition

beanDefinitionName = memberService 
beanDefinition = Generic bean: class [hello.core.member.MemberServiceImpl]; 
scope=; 
abstract=false; 
lazyInit=false; 
autowireMode=0; 
dependencyCheck=0; 
autowireCandidate=true; 
primary=false; 
factoryBeanName=null; 
factoryMethodName=null; 
initMethodName=null; 
destroyMethodName=null; 
defined in class path resource [appConfig.xml]
```
{% endraw %}

{% raw %}
```java
자바 설정 파일을 통한 빈 등록(팩토리 메소드를 이용) 시 BeanDefinition

beanDefinitionName = memberService 
beanDefinition = Root bean: class [null]; 
scope=; 
abstract=false; 
lazyInit=null; 
autowireMode=3; 
dependencyCheck=0; 
autowireCandidate=true; 
primary=false; 
factoryBeanName=appConfig; 
factoryMethodName=memberService; 
initMethodName=null; 
destroyMethodName=(inferred); 
defined in hello.core.AppConfig
```
{% endraw %}

> 💡 밑줄 친 부분을 보면, 직접 등록하는 부분은 해당 빈이 어떤 클래스를 빈으로 띄우는 지가 BeanDefinition으로 알 수 있지만, 설정파일을 통한 빈 등록 방식은 클래스 명이 비어있는 대신 어떤 팩토리의 어떤 메소드 명을 통해 빈으로 등록했는 지를 알 수 ㅣㅇㅆ다.
