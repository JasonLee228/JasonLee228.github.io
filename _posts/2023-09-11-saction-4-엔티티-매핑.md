## 객체와 테이블 매핑

### @Entity

- @Entity 가 붙은 클래스는 JPA에서 관리, 엔티티라고 한다.
    - JPA가 관리하는 객체, 테이블이 된다.

- JPA를 사용해서 테이블과 매핑할 클래스는 @Entity 필수

- ⛔주의
    - 기본 생성자 필수(파라미터가 없는 public 또는 protected 생성자)

    - final 클래스, enum, interface, inner 클래스 사용X

    - 저장할 필드에 final 사용 X

#### @Entity - 속성

- name 속성
    - JPA 에서 사용할 엔티티 이름을 지정한다.

    - 기본값: 클래스 이름
          - 가급적이면 기본값을 사용하도록 한다.

### @Table

- 엔티티와 매핑할 테이블 지정

#### @Table - 속성

- name: 매핑할 테이블 이름 - 기본값으로 엔티티 이름 사용

- catalog: 데이터베이스 catalog 매핑

- schema: 데이터베이스 스키마 매핑

- uniqueConstraints(DDL): DDL 생성 시에 유니크 제약 조건 생성

## 데이터베이스 스키마 자동 생성

- DDL을 애플리케이션 실행 시점에 자동 생성

- 테이블 중심 → 객체 중심
    - 테이블 변경때마다 변경시켜줘야 했던 객체 → 테이블 중심

    - 객체를 중심으로 확인

- 데이터베이스 방언 별로 현재 설정된 데이터베이스에 맞는 DDL 사용한다.

> 🚫 운영에서 건들지 말자.

#### 속성

![image](/assets/images/8c6084539e18478fbbb5d303616f2f6e.png)

- persistence.xml 파일의 [`hibernate.hbm2ddl.auto`](http://hibernate.hbm2ddl.auto) 옵션을 통해서 설정 가능하다.

|   |   |
| --- | --- |
| 옵션 | 설명 |
| create | 애플리케이션 실행 시 기존테이블 삭제 후 다시 생성(drop → create) |
| create-drop | create 와 같지만, 애플리케이션 종료 시에 drop (테스트 용도로 사용) |
| update | 변경분만 반영(컬럼(필드)이 지워진건 반영되지 않는다.) |
| validate | 엔티티와 테이블이 정상 매핑되었는지 확인. 비정상일 경우에 오류 |
| none | 사용 x |

> 🚫 운영 서버에서는 create, create-drop, update 사용하지 말자.
> 써도 validate 정도만.

#### DDL 생성 기능

- DDL 생성 기능은 DDL 을 자동 생성할 때만 사용되고 실제 JPA의 실행 로직에는 영향을 주지 않는다.

- 컬럼에 제약조건 추가 - `@Column` 어노테이션 사용

- 속성(아래 속성보다 몇 개 더 있기는 하다.)

|   |   |
| --- | --- |
| 옵션 | 설명 |
| name | Mapping할 Column의 이름을 지정. |
| nullable | true/false로 null 허용 여부 설정 |
| unique | true/false로 Unique 제약 조건 설정 |
| length | Column 속성 길이 설정 |
| columnDefinition | DB Column 정보를 직접 설정 |
| precision, scale | BigDecimal, BigInteger Type에서 사용,precision은 소수점 포함 전체 자릿수,scale은 소수 자릿수,double, float Type에는 적용되지 않음.아주 큰 숫자나 정밀한 소수를 다룰때 사용. |

## 필드와 컬럼 매핑

{% raw %}
```java
@Entity
public class Member {
    @Id
    private Long id;

    @Column(name = "name")
    private String username;

    private Integer age;

    @Enumerated(EnumType.STRING)
    private RoleType roleType;

    @Temporal(TemporalType.TIMESTAMP)
    private Date createdDate;

    @Temporal(TemporalType.TIMESTAMP)
    private Date lastModifiedDate;

    @Lob
    private String description;

    public Member() {
    }
}
```

### 매핑 어노테이션 정리

|   |   |
| --- | --- |
| 어노테이션 | 설명 |
| @Column | 컬럼 매핑 |
| @Temporal | 날짜 타입 매핑 |
| @Enumerated | enum 타입 매핑 |
| @Lob | BLOB, CLOB 매핑<br>varchar 를 넘어서는 큰 용량의 데이터를 저장할 시 사용 |
| @Transient  | 특정 필드를 컬럼에 매핑하지 않음(매핑 무시)<br>해당 어노테이션이 사용된 필드는 데이터베이스 컬럼이 생기지 않는다. |

#### @Column

|   |   |   |
| --- | --- | --- |
| 속성 | 설명 | 기본값 |
| name | Mapping할 Column의 이름을 지정. | 필드 이름 |
| insertable<br>updatable | 등록, 변경 가능 여부 | TRUE |
| nullable(DDL) | true/false로 null 허용 여부 설정<br>false 일 시 DDL 생성때 notNull 제약조건이 붙는다. |   |
| unique(DDL) | true/false로 Unique 제약 조건 설정<br>`@Table` 의 uniqueConstraints 와 같지만, 간단하게 한 컬럼에 제약조건 걸 때 사용 → 유니크 제약조건 아이디가 랜덤스트링이기 때문에 잘 사용하지 않고, `@Table` 에서 키네임을 지정하여 사용. |   |
| columnDefinition<br>(DDL) | DB Column 정보를 직접 설정<br>Ex) varchar(100), default ‘c’ 등,,, | 필드의 자바 타입, <br>방언 정보 이용해 기본값 설정 |
| length(DDL) | Column 속성 길이 설정 | 255 |
| precision, scale<br>(DDL) | BigDecimal, BigInteger Type에서 사용, <br>precision은 소수점 포함 전체 자릿수, <br>scale은 소수 자릿수, <br>double, float Type에는 적용되지 않음.<br>아주 큰 숫자나 정밀한 소수를 다룰때 사용. | precision=19<br>scale=2 |

#### @Enumerated

- 자바의 enum 타입 매핑시 사용

|   |   |   |
| --- | --- | --- |
| 속성 | 설명 | 기본값 |
| value | EnumType.ORDINAL: enum 순서를 데이터베이스에 저장<br>EnumType.STRING: enum 이름을 데이터베이스에 저장 | EnumType.ORDINAL |

> 🚫 EnumType.ORDINAL 사용하지 않기
> 순서를 저장할 경우 실제 사용하는 enum 의 순서가 변경됐을 시 혼동 가능성 많음.

#### @Temporal

- 날짜 타입(java.util.Date, java.util.Calendar)을 매핑할 때 사용

- 자바 8 이상에서 LocalDate, LocalDateTime 사용 시에는 생략 가능하다. → 그냥 이거 쓰자 🙂

|   |   |
| --- | --- |
| 속성 | 설명 |
| value | TemporalType.DATE: 날짜, 데이터베이스 date 타입과 매핑<br>(예: 2013–10–11)<br><br>TemporalType.TIME: 시간, 데이터베이스 time 타입과 매핑<br>(예: 11:11:11)<br><br>TemporalType.TIMESTAMP: 날짜와 시간, 데이터베이스<br>timestamp 타입과 매핑(예: 2013–10–11 11:11:11) |

#### @Lob

- 데이터베이스 BLOB, CLOB 타입과 매핑

- 매핑하는 필드 타입이 문자면 CLOB, 나머지는 BLOB
    - CLOB: String, char[], java.sql.CLOB

    - BLOB: byte[], java.sql. BLOB

#### @Transient

- 필드 컬럼에 매핑X

- 데이터베이스에 저장하는 값이 아닌 메모리에서만 사용할 필드에서 사용.

#### IDENTITY 전략

- 기본 키 생성을 데이터베이스에 위임

- 로직에서 키를 생성하여 INSERT 하지 않는다.
    - `NULL` 로 전달하면 데이터베이스에서 알아서 생성됨

    - AUTO_INCREMENT 는 데이터베이스 INSERT SQL 실행 이후에 ID값을 알 수 있다.

    - JPA 에 의해 관리되기 위해서는 PK값이 필요
      → JPA에서 식별하기 위해서 IDENTITY 전략 사용 시에는  
      `em.persist()` 시점에 INSERT SQL 실행  
      → DB에서 식별자 조회(`tx.commit()` 때가 아니라..)

{% raw %}
```java
@Entity 
public class Member { 
	@Id 
	@GeneratedValue(strategy = GenerationType.IDENTITY) 
	private Long id;
...
```
{% endraw %}

#### SEQUENCE 전략

- 데이터베이스 시퀀스는 유일한 값을 순서대로 생성하는 데이터베이스 오브젝트이다.

- 오라클, PostrgreSQL, DB2, H2 DataBase 에서 사용

- em.persist() 때 영속화하기 위해서는 PK가 필요
    - 시퀀스에 해당 테이블에서 사용중인 시퀀스의 다음 시퀀스 값을 요청해 얻어온 뒤,  엔티티에 저장 → 영속성 컨텍스트에 저장

    - IDENTITY 와 다르게 commit() 할 때 실제 INSERT SQL 실행

{% raw %}
```java
@Entity
@SequenceGenerator(
	      name = “MEMBER_SEQ_GENERATOR", 
        sequenceName = “MEMBER_SEQ", //매핑할 데이터베이스 시퀀스 이름
        initialValue = 1, allocationSize = 1)
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "MEMBER_SEQ_GENERATOR")
    private Long id;
...
```
{% endraw %}

- @SequenceGenerator 옵션

|   |   |   |
| --- | --- | --- |
| 속성 | 설명 | 기본값 |
| name | 시퀀스 생성기 이름 | 필수 |
| sequenceName | 매핑할 데이터베이스 시퀀스 이름 | hibernate_sequence |
| initialValue | 시퀀스 DDL을 생성할 때 시작할 수를 지정 | 1 |
| allocationSize | 시퀀스 한 번 호출에 증가하는 수 | 50 |
| catalog, schema | 데이터베이스 카탈로그, 스키마 이름 |   |

#### TABLE 전략

- 키 생성용 테이블을 하나 만들어서 데이터베이스 시퀀스를 흉내낸다.

- 테이블을 하나 만들어서 관리하기에 성능은 떨어진다..

- `SEQUENCE` 전략과 마찬가지로 `allocationSize` 값을 사용

{% raw %}
```java
@Entity 
@TableGenerator( 
	 name = "MEMBER_SEQ_GENERATOR", 
	 table = "MY_SEQUENCES", 
	 pkColumnValue = “MEMBER_SEQ", allocationSize = 1) 
public class Member { 
	 @Id 
	 @GeneratedValue(strategy = GenerationType.TABLE, generator = "MEMBER_SEQ_GENERATOR") 
	 private Long id;
...
}
```
{% endraw %}

- @TableGenerator 속성

|   |   |   |
| --- | --- | --- |
| 속성 | 설명 | 기본값 |
| name | 생성기 이름 | 필수 |
| table | 키생성용 테이블명 | hibernate_sequences |
| pkColumnName | 시퀀스로 사용할 컬럼명 | sequence_name |
| valueColumnName | 시퀀스 값으로 사용할 컬럼명 | next_val |
| pkColumnValue | 키로 사용할 이름 | 엔티티 이름 |
| initialValue | 초기 값, 마지막으로 생성된 값 기준 | 0 |
| allocationSize | 시퀀스 한번 호출에 증가할 수 | 50 |
| catalog, schema | 데이터베이스 카탈로그, 스키마 이름 |   |
| uniqueConstrants(DDL) | 유니크 제약조건 지정 |   |

#### allocationSize

> 🛠 시퀀스 한번 호출에 증가하는 수
> 1부터 시작하고, 50으로 설정되어 있다면 메모리에 1~51까지 미리 시퀀스를 호출하여 얻어온다.
> → 51 초과 값이 필요해지기 전까지 시퀀스를 호출하지 않음

> 💡 IDENTITY 전략을 사용할 땐, 기본 키 값을 알기 위해서 em.persist 단계에서 삽입 후 키를 얻어오지만(쓰기 지연 x), 시퀀스(테이블) 을 사용하게 되면 영속화 시에 해당 트랜젝션에서 사용할 키 값을 시퀀스를 이용해서 미리 얻어와 사용한다 → insert 쿼리는 모아서 나갈 수 있게 된다.(쓰기 지연 o)
>
> JPA 는 기본 키 값을 알기 위해 시퀀스를 조회하는데, allocationSize 만큼 한번에 얻어오게 되는 것. 해당 트랜젝션에서 사용할 키를 allocationSize 만큼 조회하는 것과 다름 없다.
>
> 실제로 트랜젝션 두 개를 연결하여 사용할 경우 첫 번째 트랜젝션에서는 allocationSize 만큼, 두 번째 트랜젝션에서는  allocationSize * 2 에서 기본 키가 시작하는 것을 확인할 수 있다.
>
> 이게 최적화와 관련이 있는 것은, 컨트롤러에서의 create api 호출 등으로 insert 문이 하나씩 생성되는 경우가 있고, bulk insert 등이 필요한 경우가 있다. 이 때, 다건의 insert 문이 생성되어야 할 경우 allocationSize 만큼 한번에 조회하여 사용하니 성능면에서 이득을 볼 수 있게 되는 것이다.
>
> 트랜젝션 별로 시퀀스를 얻어와 사용하기 때문에 중간중간 빈 키값이 생길 것인데, 
> 기본 키 값이 차례대로 올라가야 한다면 해당 값은 꼭 1로 맞추어야 한다.(아니면 저장 개수와 allocationSize 를 맞추어주던가.
