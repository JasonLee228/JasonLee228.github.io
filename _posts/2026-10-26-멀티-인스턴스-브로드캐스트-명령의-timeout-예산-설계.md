## 연결을 쥔 서버가 어느 쪽인지 모른다

서버를 여러 대로 늘리면 이런 요청이 곤란해진다.

> `DELETE /sessions/{id}` — 이 연결을 닫아 달라.

클라이언트 연결(스트림)은 서버 한 대의 메모리에만 있다. 로드밸런서는 이 DELETE 요청을 아무 서버에나 보낸다. 요청을 받은 서버가 그 연결의 소유자가 아니면 닫을 방법이 없다. 이 글에서는 이 문제를 메시지 브로커로 풀면서, **timeout을 어떻게 나눠 써야 하는지**에 초점을 맞춘다.

---

## 구조: 로컬 먼저, 실패하면 broadcast

설계는 단순하다.

1. 요청을 받은 서버가 먼저 자기 메모리에서 연결을 찾아 닫는다. 성공하면 끝이다.
2. 연결이 없다는 결과(클라이언트 없음, 연결 없음, 스트림 소유권 상실)가 나오면 **모든 서버에 명령을 broadcast**한다.
3. 소유 서버만 "닫았다"는 확정 응답을 돌려준다. 다른 서버는 응답하지 않는다.
4. 요청을 받은 서버는 **가장 먼저 도착한 응답 1건**으로 HTTP 응답을 만든다.

{% raw %}
```text
HTTP 서버 B                    RabbitMQ (fanout)              서버 A (소유)    서버 C
closeSession() → 로컬 close: 연결 없음
  → convertSendAndReceive ───▶ 모든 서버의 큐 ──────────────▶ close 실행        close 시도
                                                              → SESSION_CLOSED 응답     → 연결 없음, 응답 안 함
  ◀────────────── direct reply-to ◀─────────────────────────
  → 204
```
{% endraw %}

핵심 규칙은 "**확정 결과만 응답한다**"는 것이다. 소유하지 않은 서버가 "없음"이라고 응답하면 소유 서버의 성공 응답을 가려 버릴 수 있다. 그래서 `null`을 돌려주어(Spring AMQP에서 응답 없음) 침묵하게 한다.

---

## 브로커 구성: 서버당 큐 하나, 요청당 큐는 없다

구성 요소를 정할 때 "큐가 쌓이지 않게" 하는 것이 중요했다. 이전에 큐 잔존 문제를 여러 번 겪은 서비스라면 더 그렇다.

| 요소 | 선택 | 이유 |
|---|---|---|
| exchange | fanout | 모든 서버가 명령을 받아야 한다 |
| 큐 | `AnonymousQueue` (non-durable, exclusive, auto-delete) | 서버가 종료되어 연결이 끊기면 브로커가 큐를 지운다 |
| 큐 이름 | 접두사 + base64url(UUID) | 프로세스마다 새 이름이라 재기동해도 충돌하지 않는다 |
| 응답 | direct reply-to | 응답용 임시 큐(`amq.gen-*`)를 만들지 않는다 |
| listener | 재시도 interceptor 없는 전용 container factory | 닫기 명령은 재시도하면 안 된다 |
| ack | `AUTO`, requeue 금지 | 처리 실패한 메시지가 큐로 돌아와 반복되지 않는다 |

큐는 요청마다 만들어지지 않는다. **서버당 하나**다. 실제 환경에서 확인했을 때도 서버 수와 같은 개수의 큐가 모두 consumer 1개, 대기 메시지 0개로 유지되었다.

---

## 본론: 두 timeout이 합쳐지는 순간

여기서부터가 이 글의 핵심이다. 이 방식에는 서로 다른 timeout이 두 개 있다.

- **close timeout**: 소유 서버가 연결을 닫을 때 쓰는 실행 제한 (예: 5초)
- **reply timeout**: 호출자가 응답을 기다리는 한도 (예: close timeout + 1초 = 6초)

reply timeout을 close timeout보다 길게 잡은 이유는 있다. 소유 서버가 닫는 도중에 호출자가 먼저 404를 반환하는 일을 막기 위해서다.

그런데 리뷰에서 이런 지적이 나왔다.

> 앞선 요청 때문에 명령이 큐에서 4.9초 기다렸다면, 호출자는 6초에 404를 받는다. 그런데 수신 서버는 큐 대기 시간을 빼지 않고 **새로 5초 timeout**을 준다. 실제 종료는 약 9.8초에 일어날 수 있다.

{% raw %}
```text
t=0s     호출자: 명령 발행 (reply timeout 6초)
t=0~4.9s 명령이 큐에서 대기 (앞선 요청이 처리 중)
t=4.9s   수신 서버: 명령 수신, close 시작 (timeout 5초 새로 부여)
t=6.0s   호출자: 응답 없음 → 404 반환 (실제로는 아직 닫는 중)
t=9.8s   수신 서버: close 완료 (호출자는 이미 404를 돌려줬다)
```
{% endraw %}

사용자는 404(연결 없음)를 받았는데 연결은 몇 초 뒤에 실제로 닫힌다. 결과 자체는 나쁘지 않을 수 있지만, 응답과 실제 상태가 어긋난다. 재시도나 감사 로그 같은 후속 처리가 있다면 더 문제가 된다.

### 같은 리뷰에서 찾은 만료 창 문제

보안 때문에 명령에 HMAC 서명과 발급 시각(`issuedAt`)을 넣고, 수신 쪽에서 시각 차이가 허용 범위를 넘으면 무시하게 했다. 구현 기록에는 "5초를 넘으면 전부 무시"라고 적었지만 코드는 달랐다.

{% raw %}
```java
// 만료 판정: |now - issuedAt| > replyTimeout + skew(5초) 이면 무시
boolean expired = Math.abs(now - issuedAt) > replyWaitMs + 5_000;
```
{% endraw %}

기본값으로는 `6초 + 5초 = 11초`까지 허용된다. 호출자는 6초에 포기하는데 수신자는 11초까지 close를 시작한다. 시계 차이를 허용하려고 넣은 여유(skew)가 **만료 창 전체를 넓혀 버린 것**이다.

또 하나, 브로커가 메시지에 붙이는 `expiration`(TTL)은 **큐에 머무는 동안에만** 적용된다. consumer가 prefetch로 이미 받아 간 메시지는 만료되지 않는다.

---

## 해결 방향: 발급 시각 기준으로 남은 시간만 쓴다

원칙은 호출자의 deadline을 수신자도 공유하는 것이다. timeout을 "각자 새로 받는 값"이 아니라 "**남은 예산**"으로 다룬다.

{% raw %}
```java
void handle(SessionCloseCommand cmd) {
    long now = clock.millis();
    long deadline = cmd.issuedAtMs() + replyWaitMs;   // 호출자가 포기하는 시각
    long remaining = deadline - now;

    // 이미 호출자가 포기했다면 실행하지 않는다.
    if (remaining <= 0) {
        return;                       // 응답 없음
    }
    // 미래 시각은 작은 시계 오차만 허용한다. (skew는 미래 방향에만 적용)
    if (cmd.issuedAtMs() - now > MAX_CLOCK_SKEW_MS) {
        return;
    }
    Duration closeTimeout = Duration.ofMillis(Math.min(closeTimeoutMs, remaining));
    closeSession(cmd, closeTimeout);
}
```
{% endraw %}

바뀐 점은 세 가지다.

1. **과거 방향은 skew 없이 `replyTimeout`까지만** 허용한다. 호출자가 포기한 명령은 실행하지 않는다.
2. **미래 방향만 작은 skew를 허용**한다. 서버 시계가 조금 앞선 경우를 다룬다.
3. close timeout은 `min(기본 timeout, 남은 시간)`이다. 큐에서 기다린 시간이 자동으로 차감된다.

이렇게 하면 호출자가 404를 반환한 뒤에 close가 실행되는 일이 없어진다. 분산 환경에서는 서버 시계 차이가 있으므로 `issuedAt` 대신 메시지 헤더의 상대 TTL을 쓰는 방법도 있지만, 큐 밖(prefetch, 처리 중)에서의 시간은 여전히 직접 계산해야 한다.

## 큐 자체에도 한계를 둔다

정상 경로만 보면 큐는 안전하다. 그래도 방어선을 하나 더 둘 수 있다. 큐 선언 시 argument를 준다.

{% raw %}
```java
@Bean
public Queue sessionCloseQueue() {
    Map<String, Object> args = Map.of(
            "x-message-ttl", 6_000,     // 큐에 머무는 시간 상한 (reply timeout과 맞춘다)
            "x-max-length", 100);       // 비정상 폭주 시 큐 길이 상한
    return new AnonymousQueue(new Base64UrlNamingStrategy("app-session-close."), args);
}
```
{% endraw %}

- `x-message-ttl`: 메시지 개별 `expiration`이 없는 메시지(다른 경로에서 직접 발행한 메시지 등)도 큐에 오래 머물지 않는다. classic 큐에서는 TTL이 없는 메시지가 head에 있으면 뒤 메시지의 만료 처리가 지연될 수 있다.
- `x-max-length`: consumer가 멈추더라도 큐가 무한정 커지지 않는다.

서버가 `kill -9`로 죽으면 연결이 끊긴 것으로 판단되는 데 heartbeat 시간만큼(예: 60초)이 걸린다. 그 사이에도 메시지가 TTL로 사라지므로 큐가 쌓이지 않는다.

---

## 호출자 쪽에서 알아 둘 것

- **응답이 없으면 404**로 처리한 경우, 소유 서버가 없을 때는 reply timeout만큼 늦게 404가 나온다. 이전에는 즉시 404였다. API 명세에 동작 변화를 한 줄 남겨 두는 것이 좋다.
- `convertSendAndReceive`는 호출 스레드를 reply timeout까지 막는다. 동시에 많이 들어오면 HTTP 스레드가 점유될 수 있다. 소유 서버가 없는 요청이 몰릴 때의 영향을 같이 본다.
- 롤링 배포 중에는 구버전 서버가 exchange를 몰라 응답하지 않는다. 구버전이 소유한 연결에 대한 요청은 이전과 같은 404가 된다.
- 로컬 실패와 broadcast의 구분이 중요하다. 로컬 timeout이나 일반 예외는 "이 서버가 소유자인데 실패한 것"이므로 broadcast하지 않고 그대로 오류로 처리한다.

실제 환경에서는 정상 경로의 broadcast가 수십 ms 안에 `SESSION_CLOSED` 응답을 받았다. 문제는 평소 경로가 아니라 **지연이 겹치는 경계 조건**에서 나타난다.

## 정리

| 점검 항목 | 확인할 것 |
|---|---|
| 큐 수명 | non-durable, exclusive, auto-delete인가. 요청마다 큐를 만들지 않는가 |
| 응답 큐 | direct reply-to를 쓰는가 |
| 재시도 | 닫기처럼 멱등이 아닌 명령에 재시도 interceptor가 없는가 |
| 응답 규칙 | 소유하지 않은 인스턴스는 침묵하는가 |
| timeout 예산 | 수신자가 "새 timeout"이 아니라 "발급 시각 기준 남은 시간"을 쓰는가 |
| 만료 창 | skew가 과거 방향 창을 넓히지 않는가. prefetch된 메시지는 만료되지 않음을 고려했는가 |
| 큐 방어선 | `x-message-ttl`, `x-max-length`가 있는가 |
| 호출자 | 응답 없음의 지연이 문서에 있는가. 스레드 점유 영향을 봤는가 |

브로커를 끼운 요청-응답에서는 **timeout이 한 곳에서 정해지지 않는다.** 큐 대기, 처리 시간, 응답 대기가 각자 시계를 갖는다. 예산을 호출자의 deadline 하나로 맞추고 모든 단계에서 "남은 시간"만 쓰면, 사용자에게 돌려준 응답과 실제 상태가 어긋나는 일을 줄일 수 있다.
