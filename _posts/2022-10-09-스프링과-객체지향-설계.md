#### 객체 지향 프로그래밍 (_Object Oriented Programming)_

> _객체 지향 프로그래밍은 컴퓨터 프로그램을 __**명령어의 목록으로 보는 시각에서 벗어나**__ 여러 개의 독립된 단위, 즉 __**“객체” 들의 모임으로 파악**__하고자 하는 것이다. 각각의 객체는 메시지를 주고받고, 데이터를 처리할 수 있다.   
> → 객체의 협력_

- 객체 지향 프로그래밍은 프로그램을 **유연**하고 **변경**이 용이하게 만들기 때문에 대규모 소프트웨어 개발에 많이 사용된다. 
    - 유연 / 변경 용이?
          - 블럭을 조립하듯, 부품을 갈아 끼우듯

          - → 컴포넌트를 쉽고 유연하게 변경하면서 개발할 수 있는 방법

          - → 객체 지향의 핵심, 다형성!

- 다형성?
    - 실세계와 객체 지향을 1:1로 매칭하지는 않음

    - **역할 / 구현**으로 세상을 구분한다! 

  #### 예시 - 자동차 인터페이스

  ![image](/assets/images/91947d25eeda400d8de56b1aec73c773.png)

  > ✅ 자동차 역할
  > : 운전자는 K3에서 아반떼로 자동차를 변경해도 운전하는 데에는 지장이 없음
  > 자동차는 운전자에 영향을 주지 않는다! → 운전자는 자동차에 종속적이지 않다.
  > 자동차들은 자동차 인터페이스에 따라서 구현, 운전자는 세부 구현에 대해 알지 못하고, 자동차 역할 인터페이스 만을 알면 된다. 역할에 대해서만 의존.

  > ⚠️ 운전자(클라이언트) 는 자동차의 세부 구조(구현)에 대해서 몰라도 된다.
  > 자동차들은 자동차 역할(인터페이스)만을 구현하면 된다.
  > → **자동차의 구현은 무한한 확장이 가능하다.
  > **
  >
  > - **클라이언트에 영향을 주지 않고 새로운 기능의 확장이 가능함** EX) 가솔린 → 전기 자동차(운전자에 영향을 주지 않고 자동차 인터페이스에 따라 구현함) → 새로운 자동차가 나와도 운전자는 운전법 외 다른 무언가에 대해서 더 알 필요가 없음

  #### 예시 - 연극 역할 인터페이스

  ![image](/assets/images/37f65301ee7f43bfb46544d9bbff597f.png)

  > ✅ 로미오 / 줄리엣 역할
  >
  > : 로미오 / 줄리엣 역할을 할 배우는 언제든지 대체 가능해야 함

  로미오 역할의 배우가 바뀌더라도, 줄리엣 역할에는 아무런 영향을 끼치지 않음.

    - 역할과 구분을 나누게 되면, 변경 가능한, 대체 가능하게 된다.

    - → 유연하고, 변경이 용이하다는 말의 의미

> ✅ 정리) 
>
> - 역할과 구현으로 구분하면 세상이 단순해지고, 유연해지며 변경도 편리해진다.
>
> - 중심은 클라이언트 / 역할
>     - 클라이언트는 대상의 역할(인터페이스)만 알면 된다.
>
>     - 클라이언트는 구현 대상의 내부 구조를 몰라도 된다.
>
>     - 클라이언트는 구현 대상의 내부 구조가 변경되어도 영향을 받지 않는다.
>
>     - 클라이언트는 구현 대상 자체를 변경해도 영향을 받지 않는다.

#### 자바에서의 역할과 구현

- 자바에서는** ‘다형성’**을 이용해 역할과 구현을 정리.
    - 역할 = 인터페이스

    - 구현 = 인터페이스를 구현한 클래스, 구현 객체

  > _다형성의 개념 : 다형성(polymorphism)이란 __**하나의 객체가 여러 가지 타입을 가질 수 있는 것을 의미**_

    - 인터페이스를 어떻게 구현하는가에 따라 구현체가 달라질 수 있음
          - 자동차 - 전기차, 자동차 - 가솔린차

- 객체를 설계할 때 역할과 구현을 명확히 분리

- 객체 설계 시 역할(인터페이스)을 먼저 부여하고, 역할을 수행하는 구현 객체 생성

- 중요성 : 구현 <<<<< 인터페이스

> ⚠️ 중요)
>
> - 객체는 서로 협력함. (객체의 협력)
>     - 혼자 있는 객체는 없다. 
>           - 단순 다형성 만을 생각했을 때, 인터페이스와 구현체만 있으면 객체를 생성하고 사용할 수 있는 것처럼 보임 → 물론 가능은 하다
>
>           - 클라이언트는 요청하는 대상, 서버는 응답하는 대상
>
>           - 수많은 객체로 구성된 클라이언트와 객체 서버는 서로 요청 / 응답하는 관계
>
>           - → 객체 클라이언트와 객체 서버는 서로 협력 관계를 가진다. 클라이언트는 서버가 될 수도 있고, 서버는 클라이언트가 될 수도 있다.
>
>       ![image](/assets/images/8d8c2bfb071c41948f79035e184c7d4f.png)

#### 자바에서 다형성의 구현

- 오버라이딩(Overriding) - 슈퍼 클래스를 상속받은 서브 클래스에서 슈퍼 클래스의 추상 메소드의 내부 로직을 상세화하는 것. → 하나의 인터페이스에 여러 구현체 존재 가능케 함.

예시) 리포지토리 인터페이스와 그 구현체 1, 2 → 이를 사용하는 클라이언트 클래스

{% raw %}
```java
public interface ITestRepository {

    // 구현의 대상이 되는 인터페이스

}

@Override
public class TestRepository1 implements ITestRepository{

//    ITestRepository 를 구현한 구현체 1

}

@Override
public class TestRepository2 implements ITestRepository{

    //    ITestRepository 를 구현한 구현체 2

}

public class TestService {

    private ITestRepository testRepository = new TestRepository1();
//  private ITestRepository testRepository = new TestRepository2();

}
```
{% endraw %}

> ⚠️ → testService는 다형성에 의해서 TestRepository1, 2 중 어느 구현체든 사용 가능하다. (전기차 / 다른 자동차 생각)

#### 다형성의 본질

: 인터페이스를 구현한 객체 인스턴스를 실행 시점에 유연하게 변경할 수 있다.

> **→ 클라이언트를 변경하지 않고, 서버의 구현 기능을 유연하게 변경할 수 있다.**
