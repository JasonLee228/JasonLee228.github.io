Elasticsearch index는 RDB table처럼 보일 수 있지만, 운영에서는 index를 직접 고정 이름으로만 사용하지 않는 것이 좋다. mapping 변경, reindex, rollover, 장애 대응을 위해 alias를 사이에 두는 패턴이 중요하다.

## Physical index와 alias

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| Physical index | 실제 document가 저장되는 index | `company_v1` |
| Read alias | 조회와 검색에 사용하는 안정적인 별칭 | `company_read` |
| Write alias | 저장, 수정, 삭제에 사용하는 안정적인 별칭 | `company_write` |

MVP는 모든 조회/검색은 read alias로, 모든 쓰기는 write alias로 보낸다.

{% raw %}
```text
findById/search -> *_read
save/update/delete -> *_write
```
{% endraw %}

## Alias 생성 API

{% raw %}
```javascript
PUT /company_v1/_alias/company_read
```
{% endraw %}

쓰기 alias는 `is_write_index`를 지정할 수 있다.

{% raw %}
```javascript
POST /_aliases
Content-Type: application/json

{
  "actions": [
    {
      "add": {
        "index": "company_v1",
        "alias": "company_write",
        "is_write_index": true
      }
    }
  ]
}
```
{% endraw %}

## Versioned index

운영에서는 보통 index 이름에 version을 넣는다.

{% raw %}
```text
docs_v1
docs_v2
docs_v3
```
{% endraw %}

Mapping 변경 시 새 index를 만들고 데이터를 옮긴 뒤 alias를 전환한다.

{% raw %}
```text
docs_read  -> docs_v1
docs_write -> docs_v1

reindex docs_v1 -> docs_v2

docs_read  -> docs_v2
docs_write -> docs_v2
```
{% endraw %}

`es-rhlc-mvp`는 physical index에만 `company_v1`, `docs_v1`, `comment_v1`처럼 version suffix를 둔다. read/write alias는 `company_read`, `company_write`처럼 version 없는 안정적인 이름으로 유지해 alias switch 기반 migration을 적용한다.

## MVP 인덱스 이름 규칙

| 도메인 | 범위 | physical index | read alias | write alias |
| --- | --- | --- | --- | --- |
| company | 전역 | `company_v1` | `company_read` | `company_write` |
| docs | tenant | `{companyIdLower}_docs_v1` | `{companyIdLower}_docs_read` | `{companyIdLower}_docs_write` |
| comment | tenant | `{companyIdLower}_comment_v1` | `{companyIdLower}_comment_read` | `{companyIdLower}_comment_write` |

## Index 생성 흐름

{% raw %}
```text
Repository.save(companyId, document)
  -> createIndexIfAbsent(companyId)
    -> read alias 존재 확인
    -> 없으면 mapping JSON 로드
    -> placeholder 치환
    -> physical index 생성
  -> write alias로 IndexRequest 전송
```
{% endraw %}

## Lazy creation의 장단점

| 장점 | 단점 |
| --- | --- |
| 개발과 MVP에서 편하다 | 첫 요청 latency가 커질 수 있다 |
| tenant가 실제 데이터를 쓸 때만 index가 생긴다 | 동시 생성 race condition이 생길 수 있다 |
| 별도 bootstrap API가 없어도 동작한다 | mapping 변경과 운영 통제가 어렵다 |

## Alias switch 예시

MVP에는 reindex 검증 후 stable read/write alias를 신규 physical index로 전환하는 admin API도 포함되어 있다.

{% raw %}
```text
POST /api/admin/elasticsearch/aliases/switch
Content-Type: application/json

{
  "oldPhysicalIndex": "sc_docs_v1",
  "newPhysicalIndex": "sc_docs_v2",
  "readAlias": "sc_docs_read",
  "writeAlias": "sc_docs_write"
}
```
{% endraw %}

내부적으로 안정 alias를 사용하는 운영 migration은 다음처럼 `_aliases` API를 원자적으로 수행하는 흐름과 유사하다.

{% raw %}
```text
POST /_aliases
Content-Type: application/json

{
  "actions": [
    { "remove": { "index": "acme_docs_v1", "alias": "acme_docs_read" } },
    { "add":    { "index": "acme_docs_v2", "alias": "acme_docs_read" } },
    { "remove": { "index": "acme_docs_v1", "alias": "acme_docs_write" } },
    { "add":    { "index": "acme_docs_v2", "alias": "acme_docs_write", "is_write_index": true } }
  ]
}
```
{% endraw %}

Alias는 ES index lifecycle을 운영 가능한 형태로 만드는 첫 번째 장치다. 애플리케이션은 `sc_docs_read`, `sc_docs_write` 같은 stable alias만 바라보고, 운영자는 reindex 검증 후 alias만 신규 physical index로 전환한다.
