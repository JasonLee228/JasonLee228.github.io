## 한 세션에 다 넣으면 리뷰어가 사라진다

[이전 글](/posts/ai-코딩-에이전트로-릴리즈-리뷰하기/)에서는 릴리즈 직전 리뷰를 역할별 읽기 전용 서브에이전트로 나누는 방법을 다뤘다. 이번에는 그 앞 단계, **기능 하나를 설계부터 커밋까지 끌고 가는 동안** 세션을 어떻게 나눴는지를 적는다.

처음에는 세션 하나로 했다. 설계 문서를 쓰고, 승인하고, 구현하고, 그 세션에 "리뷰해 줘"라고 했다. 결과는 예상대로였다. 자기가 쓴 코드를 자기가 리뷰하면 자기 가정을 그대로 통과시킨다. 설계 문서에 "A는 B를 보장한다"고 적어 두면, 코드가 실제로 보장하는지와 무관하게 리뷰도 "보장한다"고 쓴다.

그래서 세션을 셋으로 나누고, 리뷰는 **다른 에이전트**에게 한 번 더 받기로 했다.

---

## 세 가지 세션

{% raw %}
```text
부모 세션 (1개)
  ├─ Task 추적 문서 유지, 다음 Task 선택
  ├─ 하위 세션이 올린 설계(plan) 승인/반려
  └─ 리뷰 finding 중 "수용/보류" 판단

하위 세션 (Task마다 1개, 순차)
  ├─ plan 작성 → 부모 승인 대기
  ├─ 구현 + 테스트 + impl 문서
  └─ 필요하면 서브에이전트(검색·테스트 실행)만 사용

리뷰 세션 (읽기 전용, 2종)
  ├─ 같은 도구의 별도 세션: 코드와 문서를 대조
  └─ 다른 도구(다른 모델)의 세션: 메시지로 요청받아 독립 리뷰
```
{% endraw %}

### 부모 세션: 결정만 한다

부모는 코드를 쓰지 않는다. 하는 일은 세 가지다.

1. Task 추적 문서를 유지한다. Task 번호, 상태, 의존 관계, 리뷰 결과 요약이 한 파일에 있다.
2. 하위 세션이 올린 plan을 읽고 승인한다. 이때 "범위를 좁혀라", "이 결정은 이유를 적어라"를 돌려보낸다.
3. 회의 결정이 바뀌면 추적 문서에 반영하고, 영향받는 Task를 보류로 바꾼다.

부모가 코드를 안 만지니 컨텍스트가 오래 간다. 2주 동안 Task 8개를 같은 부모 세션으로 끌고 갔다.

### 하위 세션: Task 하나, 문서 두 개

하위 세션은 Task 하나를 받아 **plan → 구현 → impl** 순서로 간다. plan에는 범위, 변경 파일 후보, 테스트 계획, 수용 위험이 들어간다. impl에는 실제 변경, 실행한 테스트와 결과, 리뷰 반영 내역이 들어간다.

중요한 규칙은 "하위 세션은 커밋하지 않는다"였다. staged까지만 한다. 커밋 메시지 초안을 impl에 적어 두고, 사람이 diff를 보고 커밋한다. 이 규칙 하나로 "리뷰 전에 커밋돼 버리는" 사고가 없어졌다.

### 리뷰 세션: 읽기 전용, finding ID

리뷰 세션에는 파일 수정 권한을 주지 않는다. 출력 형식도 고정했다.

{% raw %}
```text
[R2-M1] Major — <파일>:<라인>
  문제: ...
  재현: ...
  제안: ...
```
{% endraw %}

`R2`는 리뷰 회차, `M1`은 그 회차의 첫 Major다. 이 ID가 있어야 "R2-M1은 반영, R2-m2는 보류"처럼 추적 문서에 한 줄로 남는다.

## 두 에이전트 교차 리뷰

같은 도구의 별도 세션으로 리뷰해도 어느 정도 효과가 있다. 하지만 같은 모델은 같은 방향으로 틀린다. 그래서 **다른 도구의 에이전트**에게 한 번 더 리뷰를 받았다. 두 세션은 에이전트 간 메시지 도구로 연결했다. 하위 세션이 "repo, branch, 대상 파일, 리뷰 기준"을 담은 요청을 보내면, 상대 세션이 수신·착수·완료를 회신한다.

2주 동안 교차 리뷰가 잡은 것 중 같은 도구 리뷰가 놓친 것을 꼽으면 이렇다.

- **정책 출처 불일치**: 한 단계는 "다운로드 출처 URL의 정책"을, 다음 단계는 "연결의 현재 페이지 정책"을 읽었다. 현재 페이지가 허용이고 출처가 차단이면 차단이 허용으로 뒤집혔다. 설계 문서에는 둘이 같은 정책이라고 적혀 있었고, 같은 도구 리뷰는 그 문장을 믿었다.
- **끝 상태 되돌림**: 읽어둔 snapshot을 무조건 저장해 `CLOSED`가 `FALLBACK`으로 되돌아가는 경합. 독립 상태 저장 테스트는 모두 통과하던 상태였다.
- **SDK 업그레이드의 숨은 변경**: 의존 SDK가 콜백을 동기 호출에서 stream별 큐로 바꿨고, 종료된 stream의 큐를 계속 비웠다. 재연결 뒤 옛 콜백이 최신 정책을 덮을 수 있었다. 우리 코드 diff만 보면 `pom.xml` 한 줄이다.
- **timeout과 정상 완료의 경합**: timeout 종결을 scheduler로 넘긴 뒤, 큐에서 기다리는 동안 늦은 평가가 먼저 저장될 수 있다는 지적. 기존 테스트 583건은 모두 통과했지만 이 교차는 덮지 않았다.

공통점이 있다. 전부 **"문서가 그렇다고 하니까"를 믿지 않고 소스를 따라간 결과**다. 다른 모델이라서가 아니라, 우리 설계 문서를 작성한 맥락을 공유하지 않는 세션이라서 가능했다.

## 운영하면서 정한 규칙

**교차 리뷰는 승인제다.** 다른 에이전트의 사용량을 쓰므로 하위 세션이 마음대로 요청하지 않는다. 사람이 "이번 Task는 교차 리뷰까지"라고 정한다. 작은 Task는 같은 도구 리뷰로 끝낸다.

**리뷰어는 테스트를 돌리지 않을 수 있다.** 리뷰 세션 환경에서 DB·소켓이 필요한 테스트가 안 돌 때가 있다. 그 경우 "미실행"이 아니라 "환경 오류로 중단"이라고 적게 했다. 이 둘을 구분하지 않으면 다음 사람이 "테스트가 없다"로 읽는다.

**finding은 "수정 후 커밋" / "커밋 가능" 둘 중 하나로 끝난다.** Major가 하나라도 남으면 전자다. Minor만 남으면 후자이고, Minor는 추적 문서에 남겨 다음 Task에서 처리한다.

**리뷰 요청 메시지에 기준을 넣는다.** "리뷰해 줘"가 아니라 "plan §2.3의 수용 위험이 실제로 수용 가능한지, 테스트가 그 경합을 덮는지"처럼 쓴다. 기준이 없으면 리뷰어가 코딩 스타일을 본다.

**메시지 수신 확인을 기다린다.** 에이전트 간 메시지는 가끔 누락됐다. 보낸 쪽은 상대의 "수신" 회신이 올 때까지 다음 단계로 가지 않는다.

## 비용

세션이 셋이고 리뷰가 둘이니 토큰은 분명 더 쓴다. 대신 두 가지가 줄었다.

- **되돌리는 커밋.** 2주 동안 리뷰 뒤에 revert한 커밋은 없었다. 그 전 2주에는 둘 있었다.
- **"이게 왜 이렇게 됐지"를 찾는 시간.** plan·impl·리뷰 ID가 추적 문서에 있어서, 한 달 뒤에도 결정 이유를 찾을 수 있었다.

하나 더 적어 둔다. 하위 세션이 올린 설계가 **"설계 자체를 보류"로 끝난 Task도 있었다.** 외부 시스템의 식별자 규약이 회의에서 바뀌어서다. 부모가 추적 문서에 보류 사유와 날짜를 적고 끝냈다. 세션을 나눠 두면 이런 중단도 비용이 작다.

## 정리

| 세션 | 권한 | 산출물 |
|---|---|---|
| 부모 | 문서만 | Task 추적 문서, 승인 기록 |
| 하위 | 코드 + 테스트, 커밋 금지 | plan, impl, staged 변경 |
| 리뷰(같은 도구) | 읽기 전용 | finding ID 목록 |
| 리뷰(다른 도구) | 읽기 전용, 승인제 | finding ID 목록 |

핵심은 **코드를 쓴 세션이 리뷰하지 않는 것**, 그리고 **설계 문서를 쓴 맥락이 없는 세션이 한 번은 보는 것**이다. 도구가 둘일 필요는 없지만, 둘이면 같은 방향으로 틀리는 일이 줄어든다.
