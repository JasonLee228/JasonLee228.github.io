이 문서는 Elasticsearch 7.9.3을 `es-rhlc-mvp`처럼 데이터 저장소로 사용할 때 확인해야 할 운영 항목과 용어를 정리한다.

## 운영 전 체크리스트

### Index와 mapping

- [ ] index naming 규칙이 운영 tenant 정책과 맞는가?

- [ ] `number_of_shards`, `number_of_replicas`를 index template 또는 bootstrap 정책으로 관리하는가?

- [ ] mapping 변경 시 `v2` index와 reindex, alias switch 절차가 있는가?

- [ ] `dynamic: strict`로 인해 애플리케이션 DTO와 mapping 불일치가 배포 전에 잡히는가?

- [ ] `keyword`와 `text` field 선택이 검색/정렬/집계 요구사항과 맞는가?

### Alias와 lifecycle

- [ ] 모든 read가 read alias를 사용하는가?

- [ ] 모든 write/update/delete가 write alias를 사용하는가?

- [ ] write alias에 `is_write_index`가 설정되어 있는가?

- [ ] alias switch를 원자적으로 수행하는 절차가 있는가?

- [ ] lazy creation 대신 운영 bootstrap이 필요한 tenant가 있는가?

### Refresh와 성능

- [ ] 저장 직후 검색 반영이 필요한 API와 아닌 API를 구분했는가?

- [ ] 단건 write와 bulk write의 refresh policy를 다르게 관리하는가?

- [ ] `refresh=true`를 대량 작업에서 남발하지 않는가?

- [ ] `refresh_interval`이 쓰기량과 검색 반영 요구에 맞는가?

### 삭제와 일관성

- [ ] cascade delete 실패 시 재시도할 수 있는가?

- [ ] delete-by-query task monitoring이 있는가?

- [ ] orphan docs/comment/index를 정리하는 배치가 있는가?

- [ ] 삭제 이력과 실패 로그를 운영자가 추적할 수 있는가?

- [ ] delete-by-query에 대한 throttling 또는 batch 전략이 필요한가?

### 동시성

- [ ] 다중 instance 환경에서 Redis/Redisson 분산락이 활성화되어 있는가?

- [ ] lock wait time과 lease time이 실제 삭제 데이터량에 맞는가?

- [ ] lock lease 만료 후 중복 cleanup이 발생해도 idempotent한가?

### Client와 연결

- [ ] ES 7.9.3과 RHLC 7.9.3 dependency가 일치하는가?

- [ ] timeout, connection pool, keep-alive 설정이 운영 TPS에 맞는가?

- [ ] HTTPS, basic auth, self-signed 인증서 설정을 실환경에서 검증했는가?

- [ ] Actuator health로 ES 장애를 탐지하는가?

## MVP의 현재 설정 요약

| 항목 | 현재 값/방식 |
| --- | --- |
| ES client | `RestHighLevelClient` 7.9.3 |
| Spring Data Elasticsearch | 사용하지 않음 |
| index 생성 | company는 기동 시, docs/comment는 lazy creation |
| alias | physical index version과 분리된 stable `_read`, `_write` alias |
| mapping | `src/main/resources/index/*.json`, `dynamic: strict` |
| refresh interval | `app.elasticsearch.refresh-interval: 1000` |
| 단건 refresh policy | `wait_for` |
| 댓글 bulk refresh | `false` |
| delete-by-query refresh | `true` |
| lock | Redisson 우선, Redis 비활성 시 단일 JVM fallback |
| orphan cleanup scheduler | 기본 비활성 |

## 용어집

| 용어 | 설명 |
| --- | --- |
| Cluster | 여러 Elasticsearch node가 하나의 시스템처럼 동작하는 단위 |
| Node | Elasticsearch 프로세스 하나 |
| Index | document를 저장하고 검색하는 논리적 단위 |
| Physical index | 실제 document가 저장되는 index |
| Alias | index를 가리키는 별칭 |
| Read alias | 조회/검색용 alias |
| Write alias | 저장/수정/삭제용 alias |
| Shard | index를 물리적으로 나눈 조각 |
| Primary shard | 원본 shard |
| Replica shard | primary shard의 복제본 |
| Mapping | field와 type, 분석 방식을 정의하는 schema 유사 구조 |
| Document | ES에 저장되는 JSON 데이터 단위 |
| Field | document의 속성 |
| Inverted index | term에서 document를 찾기 위한 검색용 색인 구조 |
| Doc values | 정렬, 집계, scripting에 주로 쓰는 column-oriented 저장 구조 |
| Routing | document를 어떤 shard에 배치할지 결정하는 기준 |
| `keyword` | 정확 일치, 필터, 정렬, 집계용 field type |
| `text` | full-text search용 field type |
| Analyzer | text를 token으로 나누고 정규화하는 구성 |
| Refresh | 최근 write를 검색 가능한 segment로 노출하는 작업 |
| Near real-time | write 후 검색 반영까지 약간의 지연이 있는 ES 특성 |
| `search_after` | deep pagination을 위한 cursor 방식 |
| Delete By Query | query와 일치하는 document를 삭제하는 API |
| Bulk API | 여러 write/delete 작업을 한 요청으로 보내는 API |
| Reindex | 한 index의 데이터를 다른 index로 다시 색인하는 작업 |
| Rollover | alias가 가리키는 write index를 새 index로 넘기는 작업 |
| ILM | Index Lifecycle Management |
| RHLC | RestHighLevelClient. ES 7.x 시대 Java client |
| Tenant index | 회사별로 분리된 docs/comment index |
| Lazy creation | 최초 write 시점에 index를 생성하는 방식 |

## Alias switch 운영 포인트

- Version은 physical index에만 포함하고 read/write alias는 stable name을 유지한다.

- 예: `sc_docs_v1` physical index는 `sc_docs_read`, `sc_docs_write` stable alias를 가진다.

- Mapping migration 시 `sc_docs_v2`를 만들고 `_reindex`로 데이터를 복사한 뒤 `_tasks`로 진행 상태를 확인한다.

- 검증 후 `_aliases` 또는 admin API `/api/admin/elasticsearch/aliases/switch`로 stable alias를 신규 physical index로 전환한다.

- 전환 전후 쓰기 중단, dual-write, 변경분 replay, rollback 기준을 운영 절차로 확정해야 한다.

## 7.9.3 기준 주의사항

- RHLC는 7.x 기준 client이며 최신 버전에서는 Java API Client가 권장된다.

- ES 7.9.3에서는 typed mapping 제거 흐름이 이미 진행된 상태이므로 `_doc`을 사용한다.

- 최신 Elastic Cloud Serverless의 기본 refresh interval이나 기능 설명은 7.9.3 운영 환경과 다를 수 있다.

- dense vector, ILM, data stream 등은 버전별 지원 범위와 API가 다를 수 있으므로 운영 적용 전 7.9.3 공식 문서를 확인해야 한다.

## 다음 개선 후보

1. ES 7.9.3 개발 cluster 기반 E2E 테스트 추가

1. tenant 생성 시점 index bootstrap API 추가

1. alias switch admin API와 reindex 절차를 운영 승인/검증/rollback 절차와 연결

1. delete-by-query task monitoring 추가

1. cascade delete retry queue 또는 outbox 도입

1. search_after cursor request API 노출

1. shard/replica/index template 운영 정책 확정

1. `_reindex`, `_tasks`, `_aliases` 기반 migration runbook 상세화
