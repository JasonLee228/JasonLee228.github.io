## Java 안의 Lua 문자열을 `.lua` 파일로 옮기기

Redis에서 여러 명령을 원자적으로 실행해야 해서 Lua 스크립트를 쓰다 보면, 어느새 Java 클래스 안에 text block이 수십 줄씩 쌓인다.

{% raw %}
```java
private static final DefaultRedisScript<Long> CLAIM_SCRIPT = new DefaultRedisScript<>("""
        if redis.call('EXISTS', KEYS[1]) == 1 then
          return 0
        end
        redis.call('HSET', KEYS[1], 'owner', ARGV[1])
        return 1
        """, Long.class);
```
{% endraw %}

스크립트가 늘어나면 문제가 생긴다.

- IDE가 Lua 문법을 하이라이트하거나 검사해 주지 않는다.
- Java 코드와 Lua 코드가 섞여 diff를 읽기 어렵다.
- 한 클래스에 스크립트가 열 개 넘게 있으면 클래스 자체가 길어진다.

그래서 스크립트를 `src/main/resources`의 `.lua` 파일로 옮기기로 했다. 여기서 **동작은 바꾸지 않는다**는 조건을 걸었다. 단순한 이동처럼 보이지만 확인해야 할 함정이 몇 개 있었다. 이 글은 그 함정과 방어 방법을 정리한다.

---

## 왜 "문자열이 바이트 단위로 같아야" 하는가

Spring Data Redis의 `DefaultRedisScript`는 스크립트 문자열의 SHA1을 계산한다. 실행할 때는 다음 순서로 움직인다.

1. `EVALSHA <sha1>`를 먼저 보낸다.
2. 서버에 그 SHA1의 스크립트가 없으면(`NOSCRIPT`) `EVAL <본문>`을 다시 보낸다.

문자열이 같으면 SHA1도 같고, 이미 Redis에 캐시된 스크립트를 그대로 쓴다. 반대로 공백 한 칸, 줄바꿈 하나만 달라도 SHA1이 달라진다.

- 동작은 같아도 스크립트가 새로 캐시된다. 배포 직후 `EVAL`이 한 번씩 더 나간다.
- 본문이 바뀐 것인지, 공백만 바뀐 것인지 구분하기 어려워진다.

그래서 이동의 완료 조건을 "**이동 전후 각 스크립트 문자열의 SHA1이 같다**"로 잡았다. 이 한 줄이 이동 작업 전체의 검증 기준이 된다.

## 함정 1. text block은 들여쓰기와 끝 공백을 바꾼다

Java text block은 컴파일할 때 다음 규칙을 적용한다.

- 모든 줄에 공통된 들여쓰기를 제거한다.
- 각 줄 끝의 공백을 제거한다.
- 닫는 `"""`가 새 줄에 있으면 마지막 줄바꿈을 남긴다.

그래서 파일 내용은 text block의 **컴파일 결과**와 똑같이 만들어야 한다. 눈으로 복사하면 마지막 줄바꿈이나 끝 공백에서 쉽게 어긋난다. 전환 전에 현재 문자열의 SHA1을 먼저 뽑아 두는 것이 안전하다.

{% raw %}
```java
// 이동 전: 현재 문자열 SHA1을 기록한다
String before = DigestUtils.sha1DigestAsHex(CLAIM_SCRIPT.getScriptAsString());
```
{% endraw %}

이동 후에는 파일에서 읽은 문자열의 SHA1이 같은지 비교한다.

- 파일에는 주석을 넣지 않는다. 주석을 넣으면 SHA1이 바뀌어 "본문 불변"을 검증할 수 없다. 반환 코드와 `ARGV` 의미 같은 계약 설명은 Java 상수의 Javadoc에 그대로 둔다. 호출 코드와 계약이 한곳에 있어야 리뷰가 쉽다.
- 같은 본문이라도 소유 클래스가 다르면 파일을 따로 둔다. 서로 다른 기능이 한 파일에 묶이면 한쪽 수정이 다른 쪽에 영향을 준다.

## 함정 2. Windows의 줄바꿈 변환이 SHA1을 바꾼다

가장 놓치기 쉬운 함정이다. Windows에서 Git은 흔히 `core.autocrlf=true`로 동작한다. 이 설정이면 checkout할 때 텍스트 파일의 `LF`가 `CRLF`로 바뀐다.

{% raw %}
```text
리포지토리에 저장된 파일:   ...\n
Windows checkout 결과:     ...\r\n   ← 문자열이 달라져 SHA1도 달라진다
```
{% endraw %}

개발자 PC에서는 CRLF로 읽히고, Linux 컨테이너 이미지에서 빌드하면 LF로 읽힌다. 환경마다 SHA1이 달라지고, 최악에는 Lua 안의 문자열 리터럴 줄바꿈이 달라질 수도 있다.

저장소 루트에 `.gitattributes`를 두고 Lua 파일만 `LF`로 고정한다.

{% raw %}
```gitattributes
*.lua text eol=lf
```
{% endraw %}

- 다른 파일 형식의 줄바꿈 정책은 건드리지 않는다. 범위를 `.lua`로 한정한다.
- 이미 `.gitattributes`가 없는 저장소에서는 새로 만드는 변경이므로 PR에 이유를 적어 둔다.

## 함정 3. 로딩 시점: 누락이 첫 실행까지 숨는다

Spring Data Redis에는 리소스를 바로 받는 편한 방법이 있다.

{% raw %}
```java
RedisScript<Long> script =
        RedisScript.of(new ClassPathResource("redis/claim.lua"), Long.class);
```
{% endraw %}

이 방식은 파일을 **처음 사용하는 시점에 읽는다.** 경로 오타나 패키징 누락이 있어도 애플리케이션은 정상 기동하고, 첫 Redis 호출에서야 실패한다. 테스트가 Redis를 쓰지 않는 모드(예: 메모리 구현으로 대체)로 돌면 테스트에서도 드러나지 않을 수 있다.

그래서 문자열을 즉시 읽어 `DefaultRedisScript`를 만드는 작은 helper를 두었다.

{% raw %}
```java
public final class LuaScriptLoader {

    private LuaScriptLoader() {}

    public static <T> DefaultRedisScript<T> load(String location, Class<T> resultType) {
        try (InputStream in = new ClassPathResource(location).getInputStream()) {
            String script = StreamUtils.copyToString(in, StandardCharsets.UTF_8);
            if (script.isBlank()) {
                throw new IllegalStateException("Empty Lua script: " + location);
            }
            return new DefaultRedisScript<>(script, resultType);
        } catch (IOException e) {
            throw new IllegalStateException("Cannot read Lua script: " + location, e);
        }
    }
}
```
{% endraw %}

상수 선언은 기존 형태를 거의 그대로 유지한다.

{% raw %}
```java
private static final DefaultRedisScript<Long> CLAIM_SCRIPT =
        LuaScriptLoader.load("redis/member/claim.lua", Long.class);
```
{% endraw %}

상수 초기화에서 호출하므로 **파일이 없으면 클래스 로딩 자체가 실패한다.** 누락이 기동 단계에서 드러난다. 필드 타입, 이름, 접근 제어자는 그대로이므로 호출부를 고칠 필요가 없다.

## 함정 4. Maven resource filtering이 Lua를 바꿀 수 있다

Spring Boot 프로젝트의 `pom.xml`에서 `src/main/resources`에 `<filtering>true</filtering>`이 켜져 있는 경우가 있다. 이때 `${...}`나 `@name@` 같은 표기가 빌드 시점에 값으로 치환된다.

Lua 코드에는 `${...}` 형태가 거의 없어서 당장은 문제가 없다. 하지만 앞으로 스크립트에 그런 문자열이 들어가면 **빌드 결과가 소스와 달라진다.**

- 이동 후 SHA1 비교는 소스 파일이 아니라 `target/classes`에 복사된 결과를 읽어서 확인했다. filtering을 거친 뒤의 문자열이 같은지 보는 것이다.
- filtering 설정을 바꾸는 것은 이번 범위가 아니므로 후속 판단으로 남겼다. Lua용 디렉터리를 filtering에서 제외하는 방법이 가장 단순하다.

## 이동 작업의 검증 순서

작업을 이렇게 나누면 실수를 빨리 잡을 수 있다.

1. 이동 전: 모든 스크립트 상수의 SHA1을 파일로 기록한다.
2. 이동: Lua 파일 생성, helper 추가, 상수를 `LuaScriptLoader.load`로 교체한다.
3. 이동 후: 같은 방법으로 SHA1을 다시 계산해 1번과 비교한다.
4. 테스트: 스크립트를 쓰는 클래스의 단위 테스트를 돌린다.
5. 통합 테스트: 실제 Redis(Testcontainers 등)에서 스크립트를 실행한다. 이 단계가 빠지면 "파일은 읽었는데 Lua가 깨진 경우"를 놓친다.

참고로 통합 테스트는 Docker 엔진이 꺼져 있으면 skip 처리되는 경우가 있다. exit code가 0이어도 테스트가 모두 skip일 수 있으니, 실행 건수와 skip 건수를 같이 확인한다.

## 덤. 스크립트를 이동한 김에 대체 가능한 것을 살펴봤다

이동 작업 중에 "아예 Lua가 필요 없는 스크립트도 있지 않을까" 하는 질문이 나왔다. 정리하면 이렇다.

| 스크립트 유형 | 기본 명령으로 대체 | 비고 |
|---|---|---|
| 필드 여러 개 읽고 Java에서 분기 | `HMGET` 한 번으로 가능 | `HMGET`은 한 번에 원자적인 snapshot을 읽는다. 분기는 Java에서 한다 |
| compare-and-delete | `DELEX key IFEQ value` | Redis 8.4 이상에서 추가된 명령이다. 쓰기 전에 운영 Redis 버전과 공식 문서를 확인한다 |
| compare-and-set | `SET key new IFEQ old EX ttl` | 마찬가지로 8.4 이상. 단, key가 없을 때의 의미가 다를 수 있다 |
| 조건 확인 후 갱신 | `WATCH`/`MULTI` | 가능하지만 재시도 로직이 필요해 Lua가 더 단순할 수 있다 |

주의할 점이 두 가지다.

- 새 명령은 **운영 Redis 버전**에 의존한다. 테스트 환경 이미지가 `redis:7`이면 새 명령을 쓰는 코드는 테스트도 못 돌린다. 버전은 사용하는 환경에서 직접 확인해야 한다.
- 두 명령으로 나뉘는 순간 원자성이 깨진다. 예를 들어 "key가 없으면 빈 값과 같다고 보고 덮어쓴다" 같은 의미는 `IFEQ` 하나로 표현되지 않는다.

이 정리를 보고도 이번 작업에서는 대체하지 않았다. "동작을 바꾸지 않는다"는 범위를 지키기 위해서다. 대체는 별도 작업으로 검토할 일이다. Redis Functions(`FUNCTION LOAD`)도 비슷하게 검토했지만, 배포 시 함수 등록과 버전 관리가 필요하고 Spring Data Redis에 정식 API가 없어 채택하지 않았다.

## 정리

| 함정 | 증상 | 방어 |
|---|---|---|
| text block 변환 규칙 | 끝 공백과 마지막 줄바꿈 때문에 SHA1이 달라진다 | 이동 전후 SHA1을 비교한다 |
| Windows `autocrlf` | checkout 환경마다 줄바꿈이 달라진다 | `.gitattributes`에 `*.lua text eol=lf` |
| 지연 로딩 | 파일 누락이 첫 Redis 호출까지 숨는다 | 상수 초기화에서 즉시 읽는 helper |
| resource filtering | `${...}`가 빌드에서 치환될 수 있다 | `target/classes` 기준으로 비교하고 Lua 경로를 filtering에서 제외 검토 |
| 통합 테스트 skip | 실제 Redis에서 실행되지 않은 채 통과로 보인다 | 실행 건수와 skip 건수를 같이 확인한다 |

Lua를 파일로 분리하는 일은 코드를 단순하게 만들지만, 그 안에서 **"문자열은 같아야 한다"**는 조건은 줄바꿈, 빌드 도구, 로딩 시점 같은 곳에서 쉽게 깨진다. 이동 전후 SHA1 비교 하나만 있어도 대부분의 실수를 잡을 수 있다.
