#### 1. 다양한 의존관계 주입 방법

- 생성자 주입

- 수정자 주입: setter 주입

- 필드 주입

- 일반 메서드 주입

- 생성자 주입
    - 생성자를 통한 의존관계 주입

    - 생성자 호출시점에 1번만 호출되는 것이 보장된다.

    - _**불변, 필수**_ 의존관계에 사용

> 📌 private final : 값이 무조건 설정되어야 한다!

> _스프링 빈의 경우, 생성자가 단 1개만 있다면 @Autowired를 생략해도 자동으로 의존관계가 주입된다.  
> → 생성자가 2개 이상일 경우 스프링 컨테이너는 어떤 생성자를 빈 등록용으로 사용할 지 모르기 때문에 @Autowired를 입력해 주어야 한다._

{% raw %}
```java
		private final MemberRepository memberRepository;
    private final DiscountPolicy discountPolicy;

    @Autowired
    public OrderServiceImpl(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
        this.memberRepository = memberRepository;
        this.discountPolicy = discountPolicy;
    }
```
{% endraw %}

> 📌 생성자 주입이 다른 주입방식과 다른 점
> 다른 의존관계 주입의 경우 빈 등록과 의존관계 주입의 단계가 나뉘어 진행되지만, 
> _**객체 생성 시 호출**_되는 생성자의 경우 빈 등록을 위해 객체 생성을 하는 과정에서 자동으로 생성자 주입이 일어난다.
>
> 객체 생성 → 생성자 호출 = 의존관계 주입

- 수정자 주입
    - setter → 필드의 값을 변경하는 수정자 메서드를 통해서 의존관계 주입

    - **선택, 변경** 가능성이 있는 의존관계에 사용

    - 자바 빈 프로퍼티 규약의 수정자 메서드 방식을 사용하는 방법 

{% raw %}
```java
    private MemberRepository memberRepository;
    private DiscountPolicy discountPolicy;
    
		@Autowired
    public void setMemberRepository(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }

    @Autowired
    public void setDiscountPolicy(DiscountPolicy discountPolicy) {
        this.discountPolicy = discountPolicy;
    }
```
{% endraw %}

> 참고: @Autowired 의 기본 동작은 주입할 대상이 없으면 오류가 발생한다. 주입할 대상이 없어도 동작하게 하려면 @Autowired(required = false) 로 지정하면 된다.  
> → memberRepository 가 아직 생성되지 않아도 괜찮게 하려면 해당 설정을 해주면 된다.

> 자바빈 프로퍼티 규약: 필드의 값을 직접 변경하지 않고, getXxx, setXxx 메서드(getter, setter) 를 통해 조회 / 수정할 수 있어야 한다는 규칙.

#### 1-1. 자바빈 프로퍼티 규약

> 📌 자바빈 설계규약
> - 맴버변수마다 별도의 getter / setter 존재해야 함.
> - get 메서드는 별도의 파라미터가 존재하면 안됨.
> - set 메서드는 반드시 하나 이상의 파라미터가 존재해야 함.
> - 속성(필드)은 반드시 읽기 또는 쓰기가 가능해야 함.

- 자바빈 규약을 따르는 클래스 구조의 예)

- 필드 주입
    - 필드에 바로 주입하는 방법

    - 코드가 간결해지지만, 외부 변경이 불가능해 테스트가 힘들다.
          - Mock 등을 만들어서 주입하기 힘들다.

    - DI 프레임워크가 존재하기에 가능한 주입 방법
          - → 추천하지 않는 방법이다. 사용하지 말자.

    - 필드 주입을 사용해도 되는 경우
          - 실제 코드와 관계 없는 테스트 코드

          - 스프링 설정을 목적으로 하는 @Configuration 같은 곳에서만 특별한 용도로 사용


#### 2. 옵션 처리

- 주입할 스프링 빈이 없는 경우를 대비한 옵션 처리
    - @Autowired(required = false) : 자동 주입할 대상이 없으면 수정자 메서드 자체가 호출되지 않는다.

    - @Nullable: 자동 주입할 대상이 없으면 null 입력

    - Optional<>: 자동 주입할 대상이 없으면 Optional.empty 입력

{% raw %}
```java
public class AutowiredTest {

    @Test
    void AutowiredOption() {

        // TestBean class 빈 등록
        ApplicationContext ac = new AnnotationConfigApplicationContext(TestBean.class);


    }

    static class TestBean {

        // 빈으로 등록되지 않는 Member 클래스를 통해 주입되지 않는 의존관계에 대한 테스트를 진행한다.

        // 의존관계가 없다면 이 수정자 메소드는 실행 자체가 되지 않는다.
        @Autowired(required = false)
        public void setNoBean1(Member noBean1) {
            System.out.println("noBean1 = " + noBean1);
        }

        // 자동 주입할 대상이 없다면 null 입력됨
        @Autowired
        public void setNoBean2(@Nullable Member noBean2) {
            System.out.println("noBean2 = " + noBean2);
        }

        // 자동 주입할 대상이 없으면 Optional.empty 입력
        @Autowired
        public void setNoBean3(Optional<Member> noBean3) {
            System.out.println("noBean3 = " + noBean3);
        }
    }
}
```
{% endraw %}

> 📌 실행 결과
>
> _**noBean3 = Optional.empty  
> noBean2 = null**_

#### 3. 생성자 주입을 선택해야 하는 이유

- _**“불변”**_
    - 대부분의 의존관계 주입, 아마 거의 무조건.?은 한번 일어나면 Application 종료 시까지 의존관게를 변경할 일이 없다. 오히려 그러면 안될 가능성이 높다.
          - 질문: 의존관계 변형이 필요한 예시?

    - 수정자 주입을 사용하게 되는 경우 setter 메서드를 public으로 열어야 하기 때문에 누군가 의존관계를 변형하여 주입하는 등의 일이 생길 수 있다.

    - 생성자 주입은 객체를 생성할 때 딱 1번만 호출 → 불변한 설계 가능

- 누락

> 📌 setter(수정자)를 통한 의존관계 주입 시, 순수 자바 코드를 통한 테스트를 진행할 때가 문제가 될 수 있다. 
> 순수 자바 코드에서의 테스트는 new 키워드를 통해 클래스를 생성하고 테스트를 진행하는 경우가 많은데, (Mock)
> setter 의존관계 주입 시 주입해줄 게 없어서(누락 발생) NPE 가 발생할 수 있다.
> 실행은 되지만 의존관계 주입이 누락되었기 때문에 오류가 발생할 수 있다.

{% raw %}
```java
public class OrderServiceImpl implements OrderService {

	private MemberRepository memberRepository;
	private DiscountPolicy discountPolicy;

  // 수정자 주입 방식의 의존관계 주입 형태
  @Autowired
		public void setMemberRepository(MemberRepository memberRepository) {
			this.memberRepository = memberRepository;
	}
	@Autowired
  public void setDiscountPolicy(DiscountPolicy discountPolicy) {
		  this.discountPolicy = discountPolicy;
  }
 //...
}

// 테스트 코드의 예시
@Test
void createOrder() {
 OrderServiceImpl orderService = new OrderServiceImpl();
 orderService.createOrder(1L, "itemA", 10000);
}
```
{% endraw %}

- _**final 키워드**_
    - 생성자 주입을 사용하면 필드에 final 키워드를 사용할 수 있다. → 생성자에서 혹시라도 값이 설정되지 않는 오류를 컴파일 시점에 막아준다.

    - 수정자 주입을 포함한 나머지 주입 방식은 모두 생성자 이후에 호출된다 → 필드에 _final 키워드를 사용할 수 없다._

- 결론
    - 생성자 주입 방식을 선택하는 가장 큰 이유는 스프링이라는 프레임워크에 의존하지 않고, 자바 언어의 특징을 살릴 수 있다는 것.

    - 생성자 주입 방식과 수정자 주입 방식은 동시에 사용 가능하다 → 기본으로 생성자 주입 사용, 필요 시 수정자 주입을 옵션으로 사용.

#### 5. 조회할 빈이 같은 타입으로 2개 이상 추가되어 있을 시엔? → @Autowired 필드 명 매칭, @Qualifier, @Primary

> NoUniqueBeanDefinitionException → @Autowired는 타입으로 빈을 검색한다. 때문에 같은 타입으로 여러 개의 빈을 등록했을 시 문제가 발생한다.

- 그렇다고 하위 빈으로 등록하기엔 DIP를 위배하는 짓이기 때문에 안됨.

- 해결 방법
    - @Autowired 필드 명 매칭

    - @Qualifier @Qualifier끼리 매칭 빈 이름 매칭

    - @Primary 사용

- @Autowired 필드 명 매칭 @Autowired 는 타입 매칭 시에 여러 빈이 조회되면 이름으로 추가 조회를 시도한다.(2단계 조회)
    - **질문) 생성자 주입 및 RequiredArgumen~ 어노테이션 사용 시에도 정상 동작? → **생성자가 하나만 있다면 거긴 자동으로 Autowired가 붙는 거고,,,그럼 알아서 동작할 것 같은데

- @Qualifier 사용 @Qualifier 는 추가 구분자를 붙여주는 방법이다. 주입시 추가적인 방법을 제공하는 것이지 빈 이름을 변경하는 것은 아니다.
    - @Qualifier 를 등록될 빈의 빈 등록 부분과 주입받는 부분에서 같은 이름으로 사용하여 주입받는다. → 생성자, 필드, 수정자 주입 방식 모두 사용 가능하다.

    - 1) @Qualifier 매칭 2) 빈 이름 매칭(검색한 이름 대상으로) 3) NoSuchBeanDefinitionException 발생

    - **질문) OCP 위반이 아닌가?**

- @Primary
    - 해당 어노테이션이 붙은 클래스는 주입 시 우선권을 가진다.

    - @Autowired 시에 여러 빈이 매칭되면 @Primary 가 우선권을 가진다.

{% raw %}
```java

@Primary
public class RateDiscountPolicy implements DiscountPolicy {}


@Component
public class FixDiscountPolicy implements DiscountPolicy {}
```
{% endraw %}

→ 같은 인터페이스의 구현체지만, RateDiscountPolicy 가 우선권을 가진다.

> 💡 @Qualifier, @Primary 둘 다 같은 타입의 의존관계 주입을 조절해 주는 어노테이션이지만, 
> @Primary 는 기본값처럼, @Qualifier 는 매우 상세하게 동작한다.
> 스프링: 자동<<수동, 기본<<상세
> 고로 @Qualifier가 전체적인 우선권이 더 높다.(같이 사용할 시)

#### 6. 어노테이션 직접 만들기

> 위처럼 단순히 `@Qualifier("mainDiscountPolicy")` 만 사용하는 것은 컴파일 시점에 오류를 잡지 못한다.  
> → 사용자에 오기(main → maiin)가 발생했을 때 실 실행 시 오류를 발생 시킬 가능성이 있음.

{% raw %}
```java
@Target({ElementType.FIELD, ElementType.METHOD, ElementType.PARAMETER, ElementType.TYPE, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Inherited
@Documented
@Qualifier("mainDiscountPolicy")
public @interface MainDiscountPolicy {
    // 기존에 class 에 직접 @Qualifier("mainDiscountPolicy") 를 붙여서 같은 타입의 빈이 여러개일 경우를 대비해 우선권을 쥐어줬지만,
    // 문자열로 빈을 직접 지정해 오류가 날 확률이 있기 때문에 어노테이션을 직접 만들어 mainDiscountPolicy 오기를 방지할 수 있다.
}
```
{% endraw %}

- 빈 주입 시 발생할 수 있는 오류를 미리 방지하기 위해 `@Qualifier("mainDiscountPolicy")` 를 미리 정의해둔 어노테이션을 만들고, discountPolicy를 등록하고, 주입받는 클래스에 정의해 줬다.

{% raw %}
```java
@Component
@MainDiscountPolicy
public class RateDiscountPolicy implements DiscountPolicy{...}


@Component
public class OrderServiceImpl implements OrderService{
    private final MemberRepository memberRepository;
    private final DiscountPolicy discountPolicy;
		public OrderServiceImpl(MemberRepository memberRepository, @MainDiscountPolicy DiscountPolicy discountPolicy) {
        this.memberRepository = memberRepository;
        this.discountPolicy = discountPolicy;
    }
....
}
```
{% endraw %}

> 💡 어노테이션 → 상속의 개념이 존재하지 않음.
> 어노테이션을 모아서 재정의할 수 있도록 하는 것은 스프링이 제공하는 기능이며, 기존의 자바 코드에는 해당 기능이 없다.

> ⚠️ 스프링 lombok 에서 제공하는 @RequiredArgsConstructor 는 어노테이션까지 포함시켜 만들어주지는 않는다. 
> 따라서 `@RequiredArgsConstructor` 과 `@Qualifier` 를 함께 사용하면 NoUniqueBeanDefinitionException이 발생한다.(중복 타입 존재 기준)

#### 7. 조회한 빈이 모두 필요할 때

- 위처럼 특정 타입의 빈 중 골라서 주입받는 것이 아닌, 특정 타입의 빈을 모두 조회하여 원하는 빈을 골라 사용해야 할 경우에 사용할 방법

- 할인을 정률과 정액 둘 중 골라서 사용할 수 있도록 한다면?

{% raw %}
```java
	public class AllBeanTest {

    @Test
    void findAllBean() {

        // 컴포넌트 스캔으로 빈을 등록하는 대상인 AutoAppConfig 클래스를 함께 등록해 discountPolicy 들을 가져올 수 있게 한다.
        ApplicationContext ac = new AnnotationConfigApplicationContext(AutoAppConfig.class, DiscountService.class);

        DiscountService discountService = ac.getBean(DiscountService.class);
        Member member = new Member(1L, "userA", Grade.VIP);

        int fixDiscountPrice = discountService.discount(member, 10000, "fixDiscountPolicy");
        int rateDiscountPrice = discountService.discount(member, 20000, "rateDiscountPolicy");

        assertThat(discountService).isInstanceOf(DiscountService.class);
        assertThat(fixDiscountPrice).isEqualTo(1000);
        assertThat(rateDiscountPrice).isEqualTo(2000);

    }

    static class DiscountService {

        private final Map<String, DiscountPolicy> policyMap;
        private final List<DiscountPolicy> policies;

        // AutoAppConfig 를 통해 모든 DiscountPolicy 를 주입받게 된다.
        public DiscountService(Map<String, DiscountPolicy> policyMap, List<DiscountPolicy> policies) {
            this.policyMap = policyMap;
            this.policies = policies;
            System.out.println("policyMap = " + policyMap);
            System.out.println("policies = " + policies);
        }

        public int discount(Member member, int price, String discountCode) {
            DiscountPolicy discountPolicy = policyMap.get(discountCode);
            return discountPolicy.discount(member, price);
        }

    }

}
```
{% endraw %}

> ⚠️ 특정 타입으로 Map을 생성하였고, 컴포넌트 스캔용 AutoAppConfig 클래스를 함께 빈으로 올려 DiscountPolicy 형식의 빈을 모두 조회할 수 있다.
> Map, List 모두 가능하다.

#### 8. 자동, 수동 기능의 실무 운영 기준

> ⚠️ -  결론
>
> 편리한 자동 기능을 기본으로 사용하자  
> 직접 등록하는 기술 지원 객체는 수동 등록  
> 다형성을 적극 활용하는 비즈니스 로직은 수동 등록을 고민해보기

**** 자동 빈 등록 추천의 이유**

- 최근의 스프링 부트, 비즈니스 앱 개발시에도 보면 거의 기본적으로 자동 빈 등록을 사용하고 있다.

- `@component` , `@Service` 등 자동 빈 등록을 위한 비즈니스 어노테이션 또한 많이 추가되어 사용되고 있다.

- 자동 빈 등록을 이용해도 결론적으로 DIP, OCP 는 잘 지켜질 수 있다.

**** 수동 빈 등록은 언제 사용하나?**

- 애플리케이션은 업무 로직(비즈니스 로직)과 기술 지원 로직으로 구분할 수 있다.
    - 업무 로직은 컨트롤러, 서비스, 레포지토리 등 비즈니스 요구사항으로 개발된 로직이다.

    - 기술 지원 로직은 기술 문제, AOP, 공통 로그 처리 등 기술적으로 업무 로직을 지원하기 위한 util bean등이 이에 해당할 것이다.

- 업무 로직은 그 수가 많으며, 각각의 클래스가 엇비슷한 패턴을 사용하고 있다. → 자동 적극 사용

- 기술 지원 로직은 그 수가 상대적으로 매우 적고, 애플리케이션 전체에 영향을 끼치는 부분이 많다.
    - 업무 로직과는 다르게 문제 발생 시 어디가 문제인지 명확하게 드러나지 않을 가능성이 꽤나 있다.

    - **이런 경우가 수동 빈 등록 방법을 사용할 때다!**

- _**애플리케이션에 광법위하게 영향을 미치는 기술 지원 객체는 수동 빈으로 등록해서 설정 정보로 한눈에 볼 수 있도록 하는 것이 좋다.**_

**** 다형성을 적극적으로 활용하는 경우도 수동 빈 등록을 사용하는 것이 좋다.**

- 위의 모든 빈 조회 후 동일 타입 빈 조회해 사용하는 부분을 예로 들 수 있다.
    - `DiscountPolicy` 타입으로 조회 시에 정확하게 어떤 빈이 등록되어 조회되는지 직접 로직을 따라가 찾지 않으면 찾기 힘들 수 있다.

    - 이런 경우 별도의 `config` 파일을 통해 한눈에 알아볼 수 있도록 하거나,  특정 패키지에 해당하는 빈들을 모아두는 것이 좋다.

** 자동 빈 주입 / 수동 빈 주입에 대해 스프링에서 등록 / 주입해 주는 여러 빈들의 경우는 모두 예외라고 생각하면 된다. 이는 이미 잘 되어 있고, 스프링을 통해 잘 등록되어 사용하고 있으니.

- 내가 직접 기술 지원 객체를 빈으로 등록하게 된다면, 이때 수동 빈 등록을 사용하도록 하자.
