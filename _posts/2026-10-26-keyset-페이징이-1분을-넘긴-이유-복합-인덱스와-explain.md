시계열 통계를 조회하는 API가 있었다. 조회 기간이 짧을 때는 괜찮았는데, 기간을 **1주**로 넓히면 응답이 **1분을 넘겼다.** 애플리케이션의 집계 계산, AOP, 직렬화는 병목이 아니었다. 시간은 DB의 keyset 조회 구간에서 쓰이고 있었다.

해결은 인덱스 하나였다. 이 글은 왜 인덱스가 없을 때 그렇게 느려지는지, EXPLAIN으로 무엇을 확인했는지, 그리고 인덱스를 추가해도 남는 비용이 무엇인지 정리한다.

---

## 1. 조회 구조

대상 테이블은 상점별로 1분마다 한 건씩 상태를 쌓는 시계열 테이블이다.

{% raw %}
```sql
CREATE TABLE order_stats (
    id            BINARY(16)  NOT NULL,   -- 랜덤 UUID
    shop_id     BINARY(16)  NOT NULL,   -- FK
    paid_count  INT,
    pending_count    INT,
    created_at   DATETIME(6) NOT NULL,
    updated_at   DATETIME(6),
    PRIMARY KEY (id),
    KEY fk_order_stats_shop (shop_id)
);
```
{% endraw %}

API는 기간 전체를 한 번에 읽지 않는다. 2000건씩 **keyset 페이징**으로 읽어 메모리에서 집계한다. 첫 페이지 쿼리는 다음과 같다.

{% raw %}
```sql
SELECT id, shop_id, paid_count, pending_count, created_at, updated_at
FROM order_stats
WHERE shop_id = ?
  AND created_at >= ? AND created_at <= ?
ORDER BY created_at ASC, id ASC
LIMIT 2000;
```
{% endraw %}

다음 페이지부터는 마지막으로 읽은 행의 `(created_at, id)`보다 뒤에 있는 행만 읽는다.

{% raw %}
```sql
  AND (created_at > :lastDate
       OR (created_at = :lastDate AND id > :lastId))
```
{% endraw %}

위 keyset 조건은 개념을 보이기 위한 예시다. ORM이 만드는 실제 SQL 형태는 다를 수 있다.

---

## 2. 인덱스가 없으면 무슨 일이 생기나

당시 이 테이블에는 FK 때문에 생긴 `shop_id` 단일 인덱스만 있었다.

이 상태에서 위 쿼리를 처리하려면 DB가 다음 순서로 일한다.

1. `shop_id` 인덱스로 해당 상점의 모든 행(이력 전체)을 후보로 가져온다.
2. 그중 `created_at` 범위에 맞는 행을 거른다.
3. `ORDER BY created_at, id`를 만족시키려고 **filesort**로 정렬한다.
4. 앞에서 2000건만 돌려준다.

문제는 이 일을 **페이지마다 반복한다**는 점이다. keyset 조건이 있어도 인덱스가 정렬 순서를 보장하지 못하면 매번 후보를 다시 훑는다.

규모를 추정하면 이렇다.

| 항목 | 값 |
|---|---|
| 저장 주기 | 상점당 1분에 1건 |
| 1주 조회 대상 | 7 × 1440 = 10,080건 |
| 보관 기간(3개월) 기준 상점당 최대 이력 | 약 129,600건 |
| 페이지 수 | 10,080 / 2000, 약 6회 |
| 페이지마다 훑는 후보 | 최대 약 129,600건 |

6페이지 × 129,600건이면 약 78만 건이다. PK가 랜덤 UUID이므로 행 접근은 클러스터드 인덱스를 랜덤하게 읽는 I/O다. 행 하나에 0.1ms만 잡아도 약 78초가 나온다. "1분 초과"라는 증상과 맞는 계산이다.

> 위 숫자는 추정이다. 정확한 시간은 데이터 크기와 버퍼 풀 적중률에 따라 달라진다.

---

## 3. 해결: 조건과 정렬을 함께 담는 복합 인덱스

복합 인덱스의 컬럼 순서는 **동등 조건 → 범위 조건 → 정렬 보조 컬럼** 순으로 잡는다.

{% raw %}
```sql
CREATE INDEX idx_order_stats_shop_created
    ON order_stats (shop_id, created_at, id);
```
{% endraw %}

| 컬럼 | 역할 |
|---|---|
| `shop_id` | `=` 조건. 인덱스에서 상점 구간으로 바로 진입 |
| `created_at` | 범위 조건과 정렬의 첫 키 |
| `id` | `created_at`가 같을 때의 정렬 보조 (`ORDER BY created_at, id`와 일치) |

이 인덱스는 `WHERE`와 `ORDER BY`를 한꺼번에 만족한다. DB는 인덱스의 해당 구간을 순서대로 읽으면 되고, 따로 정렬할 필요가 없다.

---

## 4. EXPLAIN으로 확인한 결과

인덱스 추가 전에는 `Extra`에 `Using filesort`가 나타났다. 추가 후의 결과는 다음과 같다.

{% raw %}
```text
+------+-------------+----------------+-------+------------------------------------+---------+-------+-----------------------+
| id   | select_type | table          | type  | key                                | key_len | rows  | Extra                 |
+------+-------------+----------------+-------+------------------------------------+---------+-------+-----------------------+
|    1 | SIMPLE      | order_stats | range | idx_order_stats_shop_created  | 24      | 22886 | Using index condition |
+------+-------------+----------------+-------+------------------------------------+---------+-------+-----------------------+
```
{% endraw %}

각 값의 의미를 읽어 보자.

- `type = range`: 인덱스 범위 스캔이다. 풀스캔이 아니다.
- `key_len = 24`: `shop_id`(16바이트)와 `created_at`(8바이트)까지 사용했다는 뜻이다. 정렬에 필요한 순서는 인덱스가 이미 만족한다.
- `Extra`에 `Using filesort`가 없다. 정렬 단계가 사라졌다.
- `Extra = Using index condition`: 인덱스 컨디션 푸시다운(ICP)이 동작한다. 그러나 `Using index`(커버링)는 아니다.
- `rows`는 약 2만 건대다. 페이지마다 이력 전체가 아니라 요청 기간의 행만 대상으로 삼는다. 이 값은 옵티마이저의 추정치이므로 실제 읽은 행 수와는 다를 수 있다.

인덱스 생성 자체는 개발 서버에서 약 3초가 걸렸다. 테이블 전체를 읽어 인덱스를 만드는 일회성 비용이며, 데이터가 많은 환경에서는 더 걸릴 수 있다.

실측 응답 시간은 대표 쿼리 기준 **약 50% 단축**됐다. 이 결과는 개발 서버의 한 시나리오 기준이므로 환경에 따라 달라질 수 있다.

---

## 5. 왜 50%만 줄었나

인덱스를 추가했는데 시간이 절반에 그친 이유가 궁금할 수 있다. EXPLAIN의 `Using index condition`이 단서다.

조회 컬럼(`paid_count`, `pending_count`, `updated_at`)은 인덱스에 들어 있지 않다. 그래서 인덱스에서 찾은 행마다 **클러스터드 인덱스(PK)로 돌아가 나머지 컬럼을 읽어야 한다.** PK가 랜덤 UUID이므로 이 접근은 여전히 랜덤 I/O다.

{% raw %}
```text
세컨더리 인덱스 range scan  (순차, 빠름)
        ↓ 행마다
PK 클러스터드 인덱스 조회   (랜덤 UUID라서 랜덤 I/O)
```
{% endraw %}

남은 비용은 이 룩업이라고 추정한다. 다만 "나머지 50%가 모두 룩업 때문"이라고 확인한 것은 아니다. 추가 검증이 필요한 추정이다.

남은 비용을 줄이는 선택지는 다음과 같다.

| 방법 | 효과 | 비용 |
|---|---|---|
| 커버링 인덱스(조회 컬럼까지 포함) | PK 룩업 제거 | 인덱스 크기와 쓰기 비용 증가 |
| PK를 시간 정렬형 ID로 변경 | 클러스터드 인덱스 접근이 순차적이 됨 | 마이그레이션 위험이 큼 |

이번에는 둘 다 적용하지 않았다. 기본 복합 인덱스만으로 큰 폭의 개선을 얻었고, 운영 반영 후 실측을 보고 다음 단계를 판단하기로 했다.

---

## 6. 인덱스를 추가할 때 함께 챙긴 것

인덱스는 DB 스키마 변경이라서 코드 변경보다 챙길 것이 많다.

- **Flyway 마이그레이션**: `CREATE INDEX IF NOT EXISTS`로 작성했다. 이미 수동으로 만든 환경에서도 실패하지 않는다.
- **테스트용 H2 마이그레이션 미러**: 테스트 스키마에도 같은 마이그레이션을 추가해야 한다. 빠뜨리면 테스트 환경과 운영 스키마가 갈라진다.
- **롤백 스크립트 위치**: Flyway는 자동 롤백을 제공하지 않는다. `DROP INDEX IF EXISTS`를 담은 참고용 스크립트를 마이그레이션 디렉터리 밖에 두어 실수로 실행되지 않게 했다.
- **빌드 시간**: 운영 반영 전에 `SELECT COUNT(*)`로 행 수를 확인해 인덱스 빌드 시간을 가늠하고, 트래픽이 적은 시간에 배포한다.

---

## 7. 정리

처음의 질문으로 돌아가면, keyset 페이징이 느린 이유는 페이징 방식이 아니라 **페이징을 받쳐 줄 인덱스가 없어서**였다.

| 문제 | 원인 | 해결 |
|---|---|---|
| 1주 조회가 1분 초과 | `WHERE` + `ORDER BY`를 만족하는 인덱스 없음 | `(shop_id, created_at, id)` 복합 인덱스 |
| 페이지마다 느림 | 매 페이지 이력 전체 후보 재탐색 | 인덱스 range scan |
| 정렬 비용 | filesort | 인덱스 순서로 정렬 대체 |
| 인덱스 후에도 남는 비용 | 랜덤 UUID PK 클러스터드 룩업 | 커버링 인덱스, PK 변경은 후속 검토 |

키셋 쿼리를 새로 만들 때의 체크리스트는 다음과 같다.

- [ ] 조회 조건과 `ORDER BY`를 함께 만족하는 복합 인덱스를 설계했는가 (동등 → 범위 → 정렬 순)
- [ ] 머지 전에 `EXPLAIN`으로 `Using filesort`와 풀스캔 여부를 확인했는가
- [ ] 시계열 테이블이라면 보관 기간 기준 최대 행 수를 계산해 보았는가
- [ ] 마이그레이션을 추가할 때 테스트용 H2 미러도 추가했는가
- [ ] 운영 반영 전에 인덱스 빌드 시간을 가늠했는가

한 가지 더 기억할 점이 있다. 개발 서버에서 얻은 **약 50% 단축**은 운영 데이터 규모에서의 결과가 아니다. 운영에서의 효과는 반영 후에 다시 측정해야 한다.
