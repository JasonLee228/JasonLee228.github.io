## # 웹 애플리케이션 이해

### 웹 서버와 웹 애플리케이션 서버

#### 웹 서버

- 정적 리소스를 요청과 응답에 의해 주고 받을 수 있는 서버

#### 웹 애플리케이션 서버(WAS - Web Application Server)

- 웹 서버의 기능도 수행 가능(정적 리소스 서빙)

- 프로그램 코드를 실행하여 애플리케이션 로직을 수행할 수 있다!

> 💡 둘의 차이 ? - WAS는 애플리케이션 로직을 실행하는 데에 특화되어 있다!
> 자바 기준 : 서블릿 컨테이너 기능을 제공하면 WAS

#### 웹 시스템의 구성

1. **WAS + DB**
  ![image](/assets/images/cc94b2ac155248798e5e623bbff233db.png)

    - WAS 는 정적 리소스(HTML, CSS …) 도 처리할 수 있고, 어플리케이션 로직도 수행할 수 있다.
      → 혼자 두고 서버 돌려도 되겠네?

      → 혼자 로직(애플리케이션 로직)도 돌리고 화면(정적 리소스)도 관리하고~

      → 펑

    - WAS 에게 너무 많은 역할을 담당하게 하면 서버에 과부하가 올 수 있다!
          - 중요도(비싼 정도) : 애플리케이션 로직 >>>>>>>>>>>>정적 리소스

          - _근데 정적리소스 보여준다고 로직돌리는데 힘 못씀_

    - 가장 중요 : WAS에 장애가 발생해 뻗으면 우리는 오류 난 화면조차 볼 수 없다.

1. **WEB Server + WAS + DB**
  ![image](/assets/images/220ff42563e8452baa9bd1b4b0e99c59.png)

    - 웹 서버 → 정적리소스 관리 가능 : 정적리소스 너 해.

    - WAS → 이제 비싼거 다 너 해!(여유)
          - WEB Server 는 로직이 필요할 때 WAS를 호출하여 로직 처리를 위임

    - 장점 
          - 효율적 리소스 관리
                  - 정적 리소스가 더 많이 사용 → 웹서버 증설

                  - 애플리케이션 리소스가 더 많이 사용 → WAS 증설

                  - 간편!

          - 장애 처리
                  - 단순히 정적인 리소스만 가져와서 클라이언트에게 제공하는 웹 서버 → 잘 안죽음

                  - 애플리케이션 상의 장애 발생 → WAS는 생각보다 잘 죽는다!
                            - WAS 장애 시 WAS는 에러코드를 남기고 죽는다

                    → 웹 서버에서 정해진 오류 화면을 클라이언트에게 제공, 원인 파악 용이

### 서블릿

![image](/assets/images/bfcff14fc7fc4e6da785fb0f3e58d377.png)

- 이러한 요청에 대해서 서블릿 기능을 지원할 때와 지원하지 않을 때 차이를 확인해 보자

![image](/assets/images/85352e62f9f740cda94f04ce45612a7b.png)

- 초록박스 말고는 사실 의미있는 비즈니스 로직 존재 x

#### 하지만 서블릿을 지원하는 WAS를 사용한다면?

![image](/assets/images/b63f7619fd004779a9be51b5fde3e916.png)

- 비즈니스 로직 하나만 사용할 수 있고, 나머지는 서블릿에서 지원한다!

#### 서블릿?

> 💡 **복잡한 웹 요청과 응답의 흐름을 간단한 메서드 호출만으로 체계적으로 다룰 수 있게 해주는 기술**

{% raw %}
```java
@WebServlet(name = "helloServlet", urlPatterns = "/hello")
public class HelloServlet extends HttpServlet {

	 @Override
	 protected void service(HttpServletRequest request, HttpServletResponse response){
			 //애플리케이션 로직
	 }
}
```
{% endraw %}

- 개발자는 서블릿을 사용하기 위해 위같은 서블릿 코드를 짜주기만 하면, HTTP 요청 / 응답 정보를 매우 편리하게 관리, 사용할 수 있다.

- urlPatterns(/hello)의 URL이 호출되면 서블릿 코드가 실행 (HTTP 요청)
    - HTTP 요청 정보를 편리하게 사용할 수 있는 `HttpServletRequest`

    - HTTP 응답 정보를 편리하게 제공할 수 있는 `HttpServletResponse` → 개발자는 HTTP 스펙을 매우 편리하게 사용 

- (서블릿을 지원하는)WAS 내부에는 **서블릿 컨테이너**가 존재
    - 서블릿 코드(HttpServlet 상속) 는 WAS 가 기동될 때 서블릿 객체를 생성하여 컨테이너에 넣어둔다.

    - 해당 서블릿에 지정한 주소로 요청이 들어오게 되면, WAS는 서블릿 컨테이너에서 해당 서블릿을 호출해 줌 → _복잡한 http 단계 스킵!_

![image](/assets/images/43438ab0f66f4da0a8a552f55a988729.png)

#### 서블릿 컨테이너 특징

- 톰캣처럼 서블릿을 지원하는 WAS를 **서블릿 컨테이너**라고 함

- 서블릿 컨테이너는 서블릿 객체를 생성, 초기화, 호출, 종료하는 **생명주기 관리**

- 서블릿 객체는 _**싱글톤으로 관리**_
    - **# Request, Response 객체가 싱글톤인게 아님! 얘네는 무조건 매번 새로 생성**

    - 고객의 요청이 올 때 마다 계속 객체를 생성하는 것은 비효율

    - 최초 로딩 시점에 서블릿 객체를 미리 만들어두고 재활용

    - 모든 고객 요청은 동일한 서블릿 객체 인스턴스에 접근

    - **공유 변수 사용 주의 → **싱글톤에 공유변수 쓰지 말라고 배웠져?

    - 서블릿 컨테이너 종료시 함께 종료

- JSP도 서블릿으로 변환 되어서 사용

- 동시 요청을 위한 멀티 쓰레드 처리 지원

#### 동시 요청 - 멀티 쓰레드

HTTP 요청이 들어오게 되면, 서블릿(servlet)이 호출되어야 함  
→ 이 호출을 쓰레드가 한다!

- 애플리케이션 코드를 하나하나 순차적으로 실행하는 것은 쓰레드이다.

- 자바 메인 메소드를 처음 실행하면 main 이라는 이름의 쓰레드가 실행됨

- 쓰레드가 없다면 자바 애플리케이션 실행이 불가능함 → 왜? 코드를 실행할 주체가 없는거니까

- 쓰레드는 한번에 하나의 코드 라인만 수행

- → 동시에 같은 코드를 실행해야 한다면(동시 처리) 쓰레드를 추가로 생성

멀티 쓰레드가 지원되지 않는 상황

- 단일 요청일 경우에는 문제 발생 x

- 단일 쓰레드에 다중 요청이 들어올 경우
    - 쓰레드는 먼저 들어온 요청을 처리

    - 먼저 들어온 요청이 끝나지도 않았는데 새 요청이 들어온다면?
      → 둘 다 정상적으로 처리되지 않을 수 있다.

      ![image](/assets/images/aa17d4819f534d0fa3df18a6868c7847.png)

#### 멀티 쓰레드 지원 - 요청 마다 쓰레드 생성

- **하나에 요청에 쓰레드 하나 **할당(생성)

- 먼저 들어온 요청의 처리 여부와 상관 없이 새로 들어온 요청에 대해 쓰레드를 생성,  서블렛 호출

- 요청 종료 시 쓰레드 해제(삭제)

![image](/assets/images/0ebb57b0b73747fb843ac5fd1ebdb062.png)

- 요청마다 쓰레드를 생성할 경우 장/단점

장점

- **동시 요청 처리** 가능

- 리소스(CPU, Memory) 허용 범위 안에서는 무한히 처리 가능

- 하나의 쓰레드가 지연되어도 나머지 쓰레드는 영향을 받지 않음

단점

- 쓰레드 생성 비용이 너무 비쌈
    - 요청마다 쓰레드 생성하면, 서버의 자원은 유한하기 때문에 점점 느려짐

- 쓰레드 - 컨텍스트 스위칭 비용 발생 서버는 실제로 병렬로 돌리고 있지 않음(코어 수의 한계) → 우리 눈에는 빨라서 그렇게 보일 뿐..

- 동시 요청이 너무 많이 오면 서버 죽음!

#### 멀티 쓰레드 지원 - 쓰레드 풀

- 쓰레드 풀이라는 쓰레드를 일정 수만큼 생성해둔 곳에 요청이 들어올 시 쓰레드를 요청하여 할당, 사용 후 반납

- 요청 마다 쓰레드 생성의 단점 보완

![image](/assets/images/cf0a8c0766a746a78aa8bc71d04a0e29.png)

- **쓰레드 풀 방식**의 특징
    - **필요한 쓰레드를 쓰레드 풀에 보관하고 관리**한다.

    - 쓰레드 풀에 생성 가능한 쓰레드의 최대치를 관리한다. 톰캣은 최대 200개 기본 설정 (변경 가능)

- 사용
    - 쓰레드가 필요하면, 이미 **생성되어 있는 쓰레드를 쓰레드 풀에서 꺼내서 사용**한다.

    - 사용을 **종료하면 쓰레드 풀에 해당 쓰레드를 반납**한다.

    - 최대 쓰레드가 모두 사용중이어서 쓰레드 풀에 쓰레드가 없으면?
          - 기다리는 요청은 거절하거나 특정 숫자만큼만 대기하도록 설정할 수 있다.

- 장점
    - 쓰레드가 미리 생성되어 있으므로, **쓰레드를 생성하고 종료하는 비용(CPU)이 절약**되고, 응답 시간이 빠르다.

    - 생성 가능한 쓰레드의 **최대치**가 있으므로 너무 많은 요청이 들어와도 **기존 요청은 안전하게 처리할 수 있다.**

#### 쓰레드 풀 방식의 Max thread - WAS 의 튜닝 포인트

- 최대 쓰레드 수를 어떻게 조절하냐에 따라 서비스의 질이 달라질 수 있다.

- 너무 낮으면?
    - 동시 요청이 많으면, 서버 리소스는 여유롭지만, 클라이언트는 금방 응답 지연

    - timeout 나는 등의 장애 발생할 수도,,,

- 너무 높으면?
    - 동시 요청이 많으면, CPU, 메모리 리소스 임계점 초과로 서버 다운

- → 적정 수를 찾아야 한다.

- 성능 테스트를 한 뒤, 적정 숫자를 찾아 적용해야 한다.

,,결론

- 멀티 쓰레드에 대한 부분은 WAS가 처리
  → 개발자는 설정만 하면 되고, 멀티 쓰레드 관련 코드들은 WAS가 다 할거니까 신경 안 써도 됨(중요!)

- 개발자는 그냥 싱글쓰레드 프로그래밍을 하듯이 편리하게 코드 개발
    - 너무 편하겐 하지 말고,, 서블릿이랑 스프링 빈은 주의!

    - 공유 변수 등의 기본적으로 주의해야 할 사항 주의.

### HTML, HTTP API, CSR, SSR

#### 정적 리소스

- 고정된 html 파일, css, js, 이미지 등 → 웹 브라우저에 이미 생성되어 있는 리소스 파일을 서버에서 전달받아 화면에 제공

#### HTML

- 동적 HTML 페이지 → 동적으로 HTML 을 생성해서 전달(view 템플릿)

#### HTTP API

- 정적 리소스(HTML) 가 아닌 데이터를 전달, 주로 JSON 형식 사용

- 다양한 시스템에서 호출

- 데이터만 주고 받음 → UI 화면이 필요하면, 클라이언트가 별도 처리
    - 앱 / 웹 클라이언트, 서버 to 서버

    - ex1) 앱 / 웹 클라이언트 ↔ 서버
          - 웹 클라이언트(자바스크립트 등)

          - 아이폰, PC 앱 등의 앱 클라이언트

          - 데이터 주고받기

    - ex2) 서버 to 서버
          - 주문 서버 ↔ 결제 서버

    - /사진첨부 필요

- 위 3가지 전달 방식은 기본적으로 HTTP 통해 데이터를 주고받는 방식.

#### SSR - 서버 사이드 렌더링

- 서버에서 최종 HTML을 생성(동적)하여 클라이언트에 전달

- HTTP 요청에 대해 응답으로 서버에서 생성한 HTML 을 전달하는 방식

- 주로 정적인 화면에 사용

- JSP, 타임리프 등 → 백엔드 개발

#### CSR - 클라이언트 사이드 렌더링

- HTML 결과를 자바스크립트를 사용해 웹 브라우저에서 동적으로 생성

- 주로 동적인 화면에 사용, 웹 환경을 마치 앱 처럼 필요한 부분부분 변경 가능
    - 지도, 캘린더 등 웹이 앱처럼 동작하게 할 수 있다.

- React, Vue Js → 프론트엔드 개발

- 클라이언트 사이드 렌더링 과정
    1. HTML 요청 → 내용이 없는 HTML, 자바스크립트 링크 전달

    1. 자바스크립트 요청 → 클라이언트 로직과 HTML 렌더링 코드가 포함된 자바스크립트 전달

    1. HTTP API 이용하여 데이터 요청 → 주로 JSON 형태의 데이터 응답

    1. 자바스크립트로 2+3 의 내용인 HTML 결과 렌더링(화면)

- /사진첨부 필요

#### 백엔드 개발을 위한 UI 기술

- SSR - JSP, 타임리프

- 화면이 정적이고, 복잡하지 않을 때 사용

- → 백엔드 필수

- CSR 은 선택
