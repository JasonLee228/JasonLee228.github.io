### 현상

java.lang.OutOfMemoryError: Java heap space 오류가 주기적으로 계속 발생

---

### 분석

운영환경은 사용량이 현저히 적음. 근데도 불구하고 주기적으로 ... 특정 상황에 발생하는 것이 아닌 서서히 차서 터진 듯한 로그 형상

발생위치를 보면 별도로 특정 로직에서 발생하는 것이 아니라 갑자기 터짐 ➡️ 누수가 발생하고 있었다는 것.

항상 보면 스케줄러는 계속 돌아가고 있었음 ➡️ 스케줄러에서 누수를 발생시킨다?

- 힙메모리를 늘리고, 스레드 수를 줄여도, 사용량이 많지 않을 때에도 발생하는 것으로 보아 어디서 누수 또는 정리되지 않은 리소스가 있는 것으로 예상하고 분석

#### 분석 결과

사용량 자체가 많지 않은 환경에서 가만히만 둬도 OOM이 발생한다는 것은, 자동으로 돌아가는 무언가에 의한 것. 스케줄러에서 외부 서비스를 1분에 한번씩 호출하는 스케줄러를 중점으로 확인

결론: `WebClient` 의 SslContext 로 인한 이슈

스케줄러의 외부 요청 호출 시에는 WebClient 를 매번 신규 생성하여 사용하도록 되어 있었는데,   
회사마다 외부 요청이 달랐기 때문에 1분에 회사 수 만큼의 WebClient 를 신규 생성하는 것.

➡️ 10개의 회사만 있다고 해도 1일에 14,000개가 넘는 WebClient 를 생성.

- WebClient 내부에는 **Netty HttpClient**가 있고, 이는:
    - `EventLoopGroup` (스레드 풀) 생성

    - `ConnectionPool` 생성

    - `SslContext` 생성

이 중 `SslContext` 의 생명주기는 GC 에 의해 관리되지 않으며 JVM 에 의해 관리되는 네이티브 객체임  
때문에 요청 스레드가 종료된다고 해도 Native 객체는 메모리를 해제하지 않기 때문에 지속적으로 메모리를 갉아먹은 것이 원인

#### 수정

프로젝트 전반의 WebClient 사용 구조를 변경:

모든 WebClient 객체는 동일 주소로는 단 1회 생성되도록 변경  
별도의 추가 설정을 진행하지 않은 SSLContext 는 공유 객체화 하여 주입받아 사용하도록 변경

결론: 좋아보인다고 맘대로 가져다 쓰지 말자
