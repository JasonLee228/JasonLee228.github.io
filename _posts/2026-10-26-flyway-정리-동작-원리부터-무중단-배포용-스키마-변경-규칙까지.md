애플리케이션 코드는 git으로 버전을 관리한다. 그런데 DB 스키마는 어떻게 관리할까? 누군가 운영 DB에 직접 `ALTER TABLE`을 실행하고, 개발 DB에는 빠뜨리고, 스테이징에는 다른 순서로 적용하면 환경마다 스키마가 조금씩 달라진다.

**Flyway**는 스키마 변경을 SQL 파일로 만들어 코드와 같이 버전을 관리하고, 애플리케이션이 뜰 때 아직 적용되지 않은 변경만 순서대로 적용해 주는 마이그레이션 도구다.

이 글은 두 부분으로 나뉜다.

1. Flyway가 무엇이고 어떻게 동작하는지, Spring Boot에서 어떻게 쓰는지
2. 롤링 배포 환경에서 마이그레이션을 안전하게 쓰는 규칙

## Flyway가 해결하는 문제

JPA를 쓰면 `spring.jpa.hibernate.ddl-auto=update`로 엔티티에 맞춰 스키마를 자동으로 바꿀 수도 있다. 하지만 운영에서는 쓰지 않는 것이 일반적이다.

- 컬럼 삭제, 이름 변경, 데이터 이관 같은 변경을 표현하지 못한다.
- 어떤 SQL이 언제 실행됐는지 기록이 남지 않는다.
- 환경마다 결과가 달라질 수 있다.

Flyway는 이것을 "변경 이력을 파일로 남기고, DB에 무엇이 적용됐는지 테이블로 기록한다"는 방식으로 해결한다. 그래서 다음이 보장된다.

- 모든 환경이 **같은 파일을 같은 순서로** 적용한다.
- 어떤 DB든 **현재 어느 버전인지** 조회할 수 있다.
- 이미 적용된 파일이 **몰래 바뀌면** 기동 시점에 잡아낸다.

## 동작 원리

애플리케이션이 시작될 때 Flyway는 다음 순서로 동작한다.

1. 설정된 위치(`locations`, 기본 `classpath:db/migration`)에서 마이그레이션 파일을 찾는다.
2. DB의 이력 테이블 `flyway_schema_history`를 읽는다. 없으면 만든다.
3. 파일 목록과 이력을 비교한다. 이미 적용된 파일은 **체크섬이 그대로인지 검증**한다.
4. 아직 적용되지 않은 버전을 **버전 순서대로** 실행한다.
5. 실행한 파일마다 버전, 설명, 체크섬, 실행 시간, 성공 여부를 이력 테이블에 남긴다.

이력 테이블은 대략 이렇게 생겼다.

| installed_rank | version | description | script | checksum | success |
|---|---|---|---|---|---|
| 1 | 1 | create orders | V1__create_orders.sql | 1234567890 | 1 |
| 2 | 2 | add status to orders | V2__add_status_to_orders.sql | -987654321 | 1 |

3번의 체크섬 검증 때문에 **한 번 적용된 마이그레이션 파일은 고치면 안 된다.** 파일을 고치면 체크섬이 달라지고, 다음 기동에서 검증이 실패해 애플리케이션이 뜨지 않는다.

## 마이그레이션 파일 종류와 이름 규칙

{% raw %}
```text
V2__add_status_to_orders.sql
│ │ └ 설명 (밑줄은 공백으로 표시된다)
│ └ 구분자: 밑줄 두 개
└ 접두사 + 버전
```
{% endraw %}

| 종류 | 접두사 | 특징 |
|---|---|---|
| Versioned | `V` | 버전 순서대로 한 번만 실행된다. 대부분의 스키마 변경은 이것이다. |
| Repeatable | `R` | 버전이 없다. 파일 내용(체크섬)이 바뀔 때마다 다시 실행된다. 모든 Versioned 실행 뒤에 돈다. 뷰, 프로시저처럼 "항상 최신 정의로 덮어쓰는" 대상에 쓴다. |
| Undo | `U` | 특정 버전을 되돌리는 스크립트다. 유료 에디션 기능이라 커뮤니티 에디션에서는 쓸 수 없다. |

이름에서 자주 실수하는 부분은 다음과 같다.

- 구분자는 **밑줄 두 개**다. `V2_add_status.sql`처럼 하나만 쓰면 Flyway가 마이그레이션으로 인식하지 않고 조용히 건너뛴다.
- 버전은 `1`, `1.1`, `2`처럼 점으로 나눌 수 있고, 숫자로 비교된다.
- 여러 브랜치에서 동시에 작업하면 같은 버전 번호가 겹치기 쉽다. 병합 직전에 최신 번호를 다시 확인한다.

## Spring Boot에서 쓰기

의존성을 추가하면 Spring Boot가 기동 시 자동으로 마이그레이션을 실행한다.

{% raw %}
```groovy
dependencies {
    implementation 'org.flywaydb:flyway-core'
    // Flyway 10부터 DB별 지원이 모듈로 분리됐다. MariaDB/MySQL은 이 모듈이 필요하다.
    implementation 'org.flywaydb:flyway-mysql'
}
```
{% endraw %}

{% raw %}
```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: false   # 기존 DB에 처음 도입할 때만 true로 검토
    validate-on-migrate: true    # 적용된 파일 체크섬 검증 (기본값 true)
    out-of-order: false          # 낮은 버전을 나중에 적용하는 것을 허용할지
    clean-disabled: true         # clean(전체 삭제) 명령 차단. 운영에서는 반드시 막는다
  jpa:
    hibernate:
      ddl-auto: validate         # 스키마 변경은 Flyway만 한다. JPA는 검증만
```
{% endraw %}

모듈 분리 여부와 각 설정의 기본값은 Flyway와 Spring Boot 버전에 따라 다를 수 있으니, 쓰는 버전의 문서를 한 번 확인하는 것이 좋다.

`ddl-auto`는 `none` 또는 `validate`로 둔다. `validate`로 두면 엔티티와 실제 스키마가 다를 때 기동 시점에 바로 알 수 있다.

### 이미 운영 중인 DB에 도입할 때: baseline

테이블이 이미 있는 DB에 Flyway를 처음 붙이면, `V1__create_orders.sql`이 이미 있는 테이블을 다시 만들려다 실패한다. 이때 **baseline**을 쓴다.

- 현재 스키마를 특정 버전(예: `1`)으로 간주하고 이력 테이블에 기록한다.
- 그 버전 이하의 파일은 실행하지 않고, 그 이후 버전만 적용한다.

`baseline-on-migrate: true`는 "이력 테이블이 없는 비어 있지 않은 DB를 만나면 자동으로 baseline한다"는 뜻이다. 편하지만, 엉뚱한 DB에 붙었을 때도 조용히 baseline해 버릴 수 있다. 도입 시점에만 켜고 이후에는 끄는 쪽이 안전하다.

### 자주 쓰는 명령

Gradle/Maven 플러그인이나 CLI로 직접 실행할 수도 있다.

| 명령 | 하는 일 |
|---|---|
| `migrate` | 미적용 마이그레이션을 적용한다. Spring Boot 기동 시 자동으로 실행되는 것이 이것이다. |
| `info` | 각 파일의 적용 여부와 현재 버전을 보여 준다. |
| `validate` | 적용된 파일과 이력 테이블의 체크섬을 비교한다. |
| `repair` | 실패 기록을 지우고 체크섬을 현재 파일 기준으로 다시 맞춘다. |
| `baseline` | 현재 스키마를 특정 버전으로 표시한다. |
| `clean` | 스키마의 모든 객체를 삭제한다. **운영에서는 절대 쓰지 않는다.** |

### 마이그레이션이 중간에 실패하면

PostgreSQL처럼 DDL을 트랜잭션으로 묶을 수 있는 DB는 실패하면 통째로 롤백된다. 하지만 **MariaDB/MySQL은 DDL이 암묵적으로 커밋**된다. 한 파일에 `ALTER` 문이 세 개 있고 두 번째에서 실패하면, 첫 번째 변경은 이미 반영된 상태로 남는다.

이 경우 이력 테이블에 `success = 0`인 행이 남고, 다음 기동은 실패한다. 복구 순서는 이렇다.

1. 부분 적용된 변경을 수동으로 확인하고 정리한다.
2. `repair`로 실패 기록을 지운다.
3. 파일을 고친 뒤 다시 `migrate`한다.

이런 상황을 줄이려면 **한 파일에 DDL 하나**를 원칙으로 두는 것이 좋다.

### 마이그레이션 테스트

마이그레이션은 실제로 쓰는 DB 엔진에서 돌려 봐야 의미가 있다. SQL 문법과 DDL 동작이 엔진마다 다르기 때문이다. 표준적인 방법은 **Testcontainers로 운영과 같은 DB 컨테이너를 띄우고** Flyway를 실행하는 것이다.

{% raw %}
```java
@SpringBootTest
@Testcontainers
class MigrationTest {

    @Container
    @ServiceConnection
    static MariaDBContainer<?> db = new MariaDBContainer<>("mariadb:11.4");

    @Autowired
    Flyway flyway;

    @Test
    void allMigrationsApplyCleanly() {
        // 컨텍스트가 뜨면서 migrate가 이미 실행됐다. 실패한 마이그레이션이 없는지 확인한다.
        assertThat(flyway.info().failed()).isEmpty();
    }
}
```
{% endraw %}

`ddl-auto: validate`와 함께 쓰면 "마이그레이션이 적용되는가"와 "엔티티와 스키마가 맞는가"를 한 번에 검증할 수 있다.

## 롤링 배포에서 지켜야 할 규칙

여기부터는 Flyway를 운영에서 쓸 때 가장 중요한 부분이다.

**마이그레이션은 되돌릴 수 없고, 이전 버전 애플리케이션은 이미 바뀐 스키마 위에서 계속 돌 수 있다.**

롤링 배포 중에는 구버전 인스턴스와 신버전 인스턴스가 같은 DB를 함께 쓴다. 배포에 문제가 생겨 이미지를 이전 버전으로 되돌려도 DB는 이전 상태로 돌아가지 않는다.

### 기본 원칙: 이전 버전 코드가 계속 동작해야 한다

모든 마이그레이션은 아래 질문을 통과해야 한다.

> 이 마이그레이션이 적용된 DB에서 **직전 버전 애플리케이션**이 정상 동작하는가?

이 질문에 "아니오"인 변경은 한 번에 배포하지 않고 여러 단계로 쪼갠다.

### 허용되는 변경 (비파괴적)

| 변경 | 조건 |
|---|---|
| 컬럼 추가 | `NULL` 허용이거나 `DEFAULT`가 있어야 한다. |
| 테이블 생성 | `IF NOT EXISTS`를 권장한다. |
| 인덱스 추가 | 대용량 테이블이면 잠금과 성능 영향을 사전에 검토한다. |
| 데이터 삽입 | 기존 데이터에 영향이 없어야 한다. |
| 컬럼 길이 확장 | 확장만 허용한다. |
| 제약조건 완화 | `IF EXISTS`를 권장한다. |

구버전 코드는 새 컬럼이나 새 테이블을 모른다. 컬럼이 `NULL`이거나 기본값이 있으면 구버전의 `INSERT`가 그 컬럼을 빼고 실행해도 성공한다.

{% raw %}
```sql
-- 안전: 구버전 INSERT가 이 컬럼을 몰라도 동작한다.
ALTER TABLE `orders`
    ADD COLUMN IF NOT EXISTS `use_gift_wrap` TINYINT(1) UNSIGNED NOT NULL DEFAULT 0;

-- 안전: NULL 허용 컬럼
ALTER TABLE `member_profiles`
    ADD COLUMN IF NOT EXISTS `status` VARCHAR(30) NULL DEFAULT NULL;
```
{% endraw %}

`ADD COLUMN IF NOT EXISTS`와 `DROP INDEX IF EXISTS`는 MariaDB 문법이다. MySQL은 지원하지 않거나 버전에 따라 다를 수 있다. 재실행 안전성(멱등성)을 높여 주기 때문에 MariaDB에서는 적극 쓴다.

### 금지하거나 제한하는 변경 (파괴적)

| 변경 | 위험 | 대응 |
|---|---|---|
| `DROP COLUMN` | 높음 | 코드에서 참조를 먼저 제거하고 배포한 뒤 삭제한다. |
| `RENAME COLUMN` | 높음 | 새 컬럼 추가, 코드 전환, 구 컬럼 삭제의 3단계로 나눈다. |
| 컬럼 타입 변경, 길이 축소 | 높음 | 확장만 허용한다. 축소는 별도 계획이 필요하다. |
| 기본값 없는 `NOT NULL` 컬럼 추가 | 높음 | 기존 행이 있으면 실패하거나, 구버전 `INSERT`가 실패한다. 기본값을 주거나 `NULL`로 추가한다. |
| `DROP TABLE` | 매우 높음 | 원칙적으로 금지한다. 불가피하면 다단계로 한다. |
| 외래키 삭제 | 중간 | 참조 무결성 영향을 분석한 뒤 진행한다. |

특히 기본값 없는 `NOT NULL` 컬럼이 자주 사고를 낸다. 이 마이그레이션은 빈 테이블에서는 성공하고 데이터가 있는 운영 DB에서 실패한다. 구버전 애플리케이션이 그 컬럼을 채우지 못해 `INSERT`가 실패하는 경우도 있다.

### 컬럼 이름을 바꾸는 법: 3번의 배포

`member_name`을 `display_name`으로 바꾸는 상황을 예로 들겠다. `RENAME COLUMN` 한 줄이면 끝나 보이지만, 구버전 코드는 `member_name`을 계속 찾는다.

**배포 1: 새 컬럼 추가 + 이중 쓰기**

{% raw %}
```sql
ALTER TABLE `members` ADD COLUMN IF NOT EXISTS `display_name` VARCHAR(100) NULL DEFAULT NULL;
UPDATE `members` SET `display_name` = `member_name` WHERE `display_name` IS NULL;
```
{% endraw %}

코드는 쓸 때 두 컬럼 모두 채우고, 읽을 때는 `display_name`이 있으면 그것을 쓴다.

**배포 2: 새 컬럼만 사용**

코드에서 `member_name` 참조를 모두 제거한다. 이 배포가 안정적이라는 것을 확인한다. 이 시점에는 이전 버전으로 롤백해도 구 컬럼이 아직 있으니 안전하다.

**배포 3: 구 컬럼 삭제**

{% raw %}
```sql
ALTER TABLE `members` DROP COLUMN IF EXISTS `member_name`;
```
{% endraw %}

세 번째 단계가 필요한 이유는 롤백 가능성 때문이다. 코드가 구 컬럼을 더 이상 쓰지 않는다는 것이 확인되기 전에 컬럼을 지우면, 롤백이 불가능해진다.

`DROP COLUMN`도 같은 방식이다. 첫 배포는 코드에서 참조만 제거하고, 컬럼 삭제는 그 배포가 안정된 다음 버전에서 한다.

### forward-only 롤백: 보상 마이그레이션

커뮤니티 에디션에는 Undo 마이그레이션이 없다. 그래서 되돌리고 싶을 때는 **변경을 되돌리는 새 마이그레이션을 추가**한다. 이를 보상 마이그레이션이라고 부른다.

지켜야 할 점은 다음과 같다.

1. **이미 적용된 마이그레이션 파일을 수정하거나 삭제하지 않는다.** 앞에서 본 체크섬 검증 때문에 애플리케이션이 뜨지 않는다.
2. 보상 마이그레이션은 새 버전 번호를 받는다. 이름에 의도를 드러낸다. (예: `V80__revert_add_status_column.sql`)
3. 보상 마이그레이션도 위의 비파괴 원칙을 따른다. 컬럼 추가를 되돌리는 것도 `DROP COLUMN` 한 방이 아니라, 코드에서 참조 제거, 안정 확인, 컬럼 삭제의 순서다.
4. `INSERT`, `UPDATE`, `DELETE`를 되돌릴 때는 데이터 손실 가능성을 먼저 검토하고, 필요하면 백업을 함께 한다.

운영 중 긴급 상황에서 Flyway 밖의 SQL을 직접 실행해야 할 때가 있다. 이런 변경은 Flyway가 모르므로 **사용한 뒤 반드시 정식 보상 마이그레이션 파일을 추가해서 이력에 반영**해야 한다. 그렇지 않으면 환경마다 스키마가 달라진다.

Undo 마이그레이션을 쓸 수 있는 환경이라도, 롤링 배포에서는 "되돌릴 수 있다"고 가정하기보다 "되돌리지 않아도 되도록 쪼개는" 편이 더 안전하다.

## 정리

| 상황 | 하는 일 |
|---|---|
| 처음 도입 | 기존 DB는 baseline으로 현재 스키마를 버전으로 표시 |
| 스키마 변경 | `V{버전}__{설명}.sql` 파일 추가, 밑줄 두 개 |
| 뷰·프로시저 | Repeatable(`R__`) 파일로 관리 |
| 적용된 파일 | 수정하지 않는다. 체크섬 검증이 실패한다 |
| 마이그레이션 실패 (MariaDB) | 부분 적용 정리, `repair`, 재실행 |
| 컬럼 추가 | `NULL` 허용 또는 `DEFAULT`를 준다 |
| 컬럼 삭제 | 코드 참조 제거 배포, 안정 확인, 삭제 마이그레이션 |
| 컬럼 이름 변경 | 새 컬럼 추가, 코드 전환, 구 컬럼 삭제의 3단계 |
| 롤백 | 이전 파일을 수정하지 않고 보상 마이그레이션을 추가 |
| 긴급 수동 SQL | 이후 정식 마이그레이션으로 이력에 반영 |
| 테스트 | Testcontainers로 운영과 같은 DB 엔진에서 실행 |

체크리스트로 줄이면 이렇다.

- [ ] 파일 이름에 밑줄 두 개를 썼는가?
- [ ] 버전 번호가 다른 브랜치와 겹치지 않는가?
- [ ] 적용된 파일을 수정하지 않았는가?
- [ ] 한 파일에 DDL을 하나만 넣었는가? (MariaDB/MySQL)
- [ ] 이 마이그레이션이 적용된 DB에서 직전 버전 앱이 동작하는가?
- [ ] 새 컬럼이 `NULL` 허용이거나 `DEFAULT`를 갖는가?
- [ ] 삭제나 이름 변경을 한 번에 하지 않았는가?
- [ ] 운영과 같은 DB 엔진에서 마이그레이션을 실행해 봤는가?
- [ ] 운영 설정에서 `clean`이 막혀 있는가?

Flyway 자체는 단순하다. 파일을 순서대로 한 번씩 실행하고, 무엇을 실행했는지 기록할 뿐이다. 어려운 부분은 도구가 아니라 **DB는 되돌릴 수 없다는 사실을 마이그레이션 설계에 반영하는 것**이다.
