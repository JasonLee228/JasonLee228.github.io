#### 좋은 객체 지향 설계의 5가지 원칙 - SOLID

클린 코드로 유명한 로버트 마틴이 좋은 객체 지향 설계의 5가지 원칙을 정리

- _SRP : 단일 책임 원칙 (Single Responsibility Principle)_

- _OCP : 개방 - 폐쇄 원칙 (open / Closed Principle)_

- _LSP : 리스코프 치환 원칙 (Liskov Subsititution Principle)_

- _ISP : 인터페이스 분리 원칙 (Interface Segregation Principle)_

- _DIP : 의존관계 역전 원칙 (Dependency Inversion Principle)_

#### SRP 단일 책임 원칙

> **하나의 클래스**는 **하나의 책임**만 가져야 한다.

> ✅ 여기서 하나의 책임이라 함은 굉장히 모호한 부분
>
> - 상황에 따라 다르고, 문맥에 따라 다름. 클 수도, 작을 수도 있다.

- 책임의 기준이 되는 것은 ‘변경’. 변경이 있을 때 파급 효과가 적으면 단일 책임 원칙을 잘 따른 것
    - 하나의 클래스 파일 안에 DB 접근, view, 쿼리 등 수많은 것이 담겨 있다면 단일 책임 원칙을 잘 따르지 못한 것이라 할 수 있다.

    - 계층 구조가 잘 나뉘어 있고, MVC 패턴 등을 잘 따르는 것이 이 SRP를 잘 따르기 위한 방법

    - 그렇다고 책임의 범위가 너무 작아도 문제 → 책임의 범위를 잘 조절하는 것이 중요!

#### OCP 개방 - 폐쇄 원칙

> 소프트웨어 요소는 확장에는 열려 있으나 변경에는 닫혀 있어야 한다.

- 기능 확장을 해야 하는데 기존 코드 변경을 하지 말라는 말? → ❌ 다형성의 활용!

- 다형성의 활용 : 인터페이스를 구현한 새로운 클래스를 생성하고, 새로운 기능을 구현(확장)한다!
    - ‘전기 모터 구동’ 이라는 새로운 기능을 도입하기 위해서 기존 자동차를 뜯어 고치지 않음

    - 자동차 역할을 구현한 ‘전기차’ 라는 구현체를 만듦

    - TestRepository1을 만든 뒤, 새로운 기능을 도입한 TestRepository2 를 구현, TestService는 2를 받아서 개발.

  {% raw %}
  ```java
  // ITestRepository repo = new TestRepository1();
  ITestRepository repo = new TestRepository2();
  ```
  {% endraw %}

  > ⚠️ 그러면 클라이언트 코드인 TestService는 변경이 일어난게 아닌가?
  >
  > - → 구현 객체를 변경하려면 클라이언트 코드를 변경해야 함 → OCP 원칙을 지킬 수 없음 이는 순수 자바 코드로 객체 지향 프로그래밍을 할 때의 한계점
  >
  > - 해결법 : 객체 생성 및 연관 관계를 맺어주는 별도의 조립, 설정자의 필요
  >
  > - 이를 **스프링**이 해준다! (IoC 컨테이너, DI를 통해)
  >     - 질문) 하나의 인터페이스에 여러 구현체가 있을 경우, 원하는 메소드를 사용하는 법은? → 이미 이 질문 자체가 스프링을 어긴 것이 된다.
  >
  > - Bean 등록 : 인터페이스, 구현 객체의 생성 및 주입은 스프링이!

#### LSP 리스코프 치환 원칙

> 프로그램의 객체는 프로그램의 **정확성을 깨뜨리지 않으면서 **하위 타입의 인스턴스로 바꿀 수 있어야 한다.

- 다형성에서 하위 클래스는 **인터페이스 규약**을 다 지켜야 한다는 것, 다형성을 지원하기 위한 원칙, 인터페이스를 구현한 구현체를 믿고 사용하려면, LSP 원칙이 필요

- 단순히 코드에 오류가 없고, 컴파일이 되는 것을 넘어서는 원칙적인 이야기
  > ⚠️ ex) ITestRepository 에 Save() 메소드가 있고, TestRepository1 에서는 이를 구현한다 가정
  >
  > - 구현체의 Save()의 구현에서 저장이 아닌 삭제를 진행하면 LSP원칙의 위반.

#### ISP 인터페이스 분리 원칙

> 특정 클라이언트를 위한 인터페이스 여러 개가 범용 인터페이스 하나보다 낫다.

- 자동차 인터페이스 분리 : ‘자동차’라는 범용적인 범위의 인터페이스로 사용하게 되면  운전만 하는 사용자에게까지 정비에 관련된 인터페이스 구현체를 넘기게 된다.(너무 크고 복잡)
    - 운전 인터페이스

    - 정비 인터페이스

- 사용자 클라이언트 분리 : 위의 분리를 통해 사용자 클라이언트의 분리 가능
    - 운전자 클라이언트

    - 정비사 클라이언트

- 분리를 통해 정비 인터페이스의 구조가 변한다 해도, 운전자 클라이언트는 운전 인터페이스만을 사용하기 때문에 영향 없음.

- 인터페이스의 역할이 명확해지고, 대체 가능성이 높아진다.

#### DIP 의존관계 역전 원칙

> 프로그래머는 추상화에 의존해야지, 구체화에 의존하면 안된다.  
> → 의존성 주입은 이 원칙을 따른다.

> ✅ 구현 클래스에 의존하지 말고, 인터페이스(**역할**)에 의존하라
>
> - 자동차를 예로 운전자는 K3에서 아반떼로 차가 바뀐다고 운전을 할 수 없는 것이 아니다. 자동차라면 운전할 수 있다.

- 객체 세상도 클라이언트가 인터페이스에 의존해야 유연하게 구현체를 변경할 수 있다.
    - 구현체에 의존하게 되면 변경에 따르기 매우 어려워 짐

- 근데 OCP에서 설명한 내용에 따르면 인터페이스에도 의존하지만, 추가 기능이 구현된 구현체에 의존하기도 한다. → TestService 서비스 클라이언트가 구현 클래스를 **직접 선택**해서 객체 생성**(구현체 의존)**

{% raw %}
```java
ITestRepository repo = new TestRepository();
```
{% endraw %}

> ✅ **→ **TestService는 ITestRepository 인터페이스의 내용 뿐 아니라, TestRepository2의 내용까지 알고 있는 것이 됨. 클래스 직접 의존.
> → DIP 위반

- 다형성 뿐 아니라, 추가적인 다른 방법을 통해 OCP / DIP를 모두 준수할 수 있도록 설계하고, 만들어야 함.

> ✅ 정리)
>
> - 객체 지향의 핵심 : **다형성**
>
> - OCP, DIP 원칙이 가장 중요한 두 원칙
>
> - 하지만
>     - 다형성 만으로는 단순히 부품 갈아끼우듯 개발할 수 없음 구현 객체의 변화가 있을 경우 클라이언트 코드가 같이 변경할 수 밖에 없는 구조
>
>     - 클라이언트 코드의 변경 없이 구현체를 변경할 수 없는가?
>
>     - 다형성 하나만으로는 OCP, DIP를 준수할 수 없다. 어딘가는 변경이 필요.

#### 객체 지향 설계와 스프링

- 스프링이 없던 시절 OCP, DIP를 준수하며 개발을 하려니 너무 복잡 → 원칙을 지켜주는 프레임워크를 개발 : 스프링!

- 순수 자바로 위 OCP, DIP 원칙을 지키며 개발을 하면 결국 스프링이, 정확히는 DI 컨테이너가 필요해짐.

> ✅ “스프링과 다형성”
>
> - 스프링은 DI을 통해 OCP, DIP를 준수하며 다형성을 가능하게 지원함
>     - DI(Dependency Injection) : 의존관계 및 의존성 주입
>
>     - DI 컨테이너 제공(컨테이너 내부에서 객체를 생성하고, 연결시켜줌)
>
> - 이를 통해 클라이언트 코드의 변경 없이 기능 확장 / 개발이 가능

#### Saction 1 정리

> ✅ 모든 설계에는 역할과 구현의 분리가 필요함(자동차, 공연 예시)
>
> - 애플리케이션 설계 또한 자동차를 설계하듯 자동차 기능 역할(역할 인터페이스)만 만들어두고, 회사들은 **언제든지 유연하게** 자동차를 개발하고 **변경**할 수 있도록 만드는 것
>
> - 또는, 공연을 설계하듯 로미오 / 줄리엣 이라는 배역만 만들어두고, 배우는 **언제든지 유연하게 변경**할 수 있도록 만드는 것이 좋은 객체 지향 설계

- 가장 이상적인 설계 : 모든 설계에 인터페이스 부여
    - 장점 : 구체적인 기술이 정해지지 않은 경우(ex. 어떤 데이터베이스를 사용할 지) 인터페이스만을 정의해두면 서비스 단 에서는 인터페이스의 메소드명만을 가져다 사용하면 되기 때문에 기술 선택 이전에 개발이 가능해짐

> ⚠️ 하지만 : 인터페이스를 무분별하게 남발할 경우 단점 발생 - 추상화 비용
>
> - 인터페이스 내부에 구현체를 까봐야 구체적인 내용을 알 수 있게 된다.
>
> ➡️ 기능을 확장할 일이 없다면, 구체화된 클래스를 직접 사용하고, 향후 필요해질 때 리팩터링하여 인터페이스를 도입해도 된다.
